# 模型评估与幻觉治理

评估先定义**用户需要什么、什么失败不可接受、证据从哪里来**，再选指标。最终交付是带版本、分母、失败样本与行动建议的判断，不是一个自动裁判均分。评测类型见 [基准深入](/evaluation/benchmarks)。

## 评估全景：五层金字塔

```
            ▲  线上评估       A/B 实验、用户反馈、业务指标（最真实，最慢）
           ▲▲  人类评估       专家标注、Chatbot Arena（金标准，贵）
          ▲▲▲  LLM-as-a-Judge 自动规模化的"准人评"（主力工具）
         ▲▲▲▲  基准测试       MMLU/GSM8K/SWE-bench…（横向可比，会饱和/污染）
        ▲▲▲▲▲  自动指标       PPL/BLEU/ROUGE（最便宜，与真实质量相关性最弱）
```

保留旧图帮助定位方法，**不是可信度/成本的普遍排序**。线上指标受人群和流程混杂，人类标签也会错，规则检查反而可能准确验证格式。五层互补，不意味着顶层可以覆盖下层未测的风险。

## 一、自动指标（基于参考答案）

PPL 不是参考答案相似度。用相同 tokenizer、文本范围与计分协议，定义 $N$ 个实际被计分 token：

$$\mathrm{PPL}=\exp\left(-\frac1N\sum_{i=1}^N\log p(x_i\mid x_{<i})\right).$$

构造三 token 概率 $(0.5,0.25,0.25)$，平均 NLL 为 $(-\log0.5-2\log0.25)/3\approx1.15525$，PPL 为 $\sqrt[3]{32}\approx3.1748$。文档边界、窗口截断、prompt/padding 是否计分都改变分母；跨 tokenizer 的 token PPL 不可直接比较，更不等于事实正确性。

| 指标 | 实际对象 | 应保留的口径 |
| --- | --- | --- |
| BLEU | 修正 n-gram precision 的组合与短句惩罚 | tokenizer、大小写、smoothing、corpus/sentence |
| ROUGE | n-gram/LCS 等匹配，可能报告 P/R/F | 具体变体、分词、stemmer、参考数量 |
| BERTScore | 上下文 token 向量匹配 | 编码器/层、语言、IDF与baseline |

[BLEU 实现](https://github.com/mjpost/sacrebleu/blob/master/sacrebleu/metrics/bleu.py) 包含 brevity penalty，不能简化为“precision”；[ROUGE 实现](https://github.com/google-research/google-research/blob/master/rouge/rouge_scorer.py) 同时返回 precision/recall/F，不能把所有 ROUGE 都叫 recall。[BERTScore 原论文](https://arxiv.org/abs/1904.09675) 的相关性结果有任务边界；相似句子也可能将“允许”改为“不允许”，需要业务事实/约束检查。

## 二、基准测试（Benchmark）

基准提供可固定的任务分布，不是通用能力证书。知识、数学、代码、长上下文、工具、安全和多模态需要不同任务与判分。先写 dataset 版本/子集、prompt、工具与采样预算、harness/judge 版本，再比较。

污染风险、题集饱和、题型不匹配和评判误差都可能影响判断；不能未经检查就把高分归为污染，也不能把低分归为模型没有该能力。完整能力地图、pass@k 和配对统计见 [评测基准](/evaluation/benchmarks)。

## 三、人类评估

人类参照应有 rubric、标注者资格、独立标注、分歧仲裁和版本。pointwise、pairwise 与排序的统计对象不同；多人一致性低可能来自标签噪声、类别不平衡、难度或参照本身不明确，不只有“题太主观”。

Chatbot Arena 测参与者在平台任务分布上的偏好，不是领域事实真值。匿名减少身份线索，但文风、长度和题型分布仍可能偏。高风险业务的专家参照不能由大众偏好分数替代。

## 四、LLM-as-a-Judge（重点）

深读 [裁判校准](/evaluation/judge-calibration)。选择模型裁判是为了扩展标注量，不是因为“强模型就是正确裁判”。

| 用法 | 适合回答 | 需校准 |
| --- | --- | --- |
| Pointwise | 是否满足给定 rubric / 分档 | 跨样本评分尺度与阈值 |
| Pairwise | 同输入两候选谁更好 | 候选身份、位置偏差、平局与弃判 |
| Reference-based | 是否符合参考/证据 | 参考不完整/过期、合理替代表达 |

[MT-Bench 研究](https://arxiv.org/abs/2306.05685) 分析位置、冗长、自我偏好和推理局限。缓解措施仍需本地对照：交换位置后恢复候选身份；长度/格式对照须保持内容；多裁判可能共享错误；匿名也不排除回答中的身份暗示。

**顺序分歧不是内容平局**。两次裁判不一致应单列“顺序不稳定/弃判”；若强行判平会隐藏失败并改变胜率。报告有效判定覆盖率、人工参照混淆矩阵、危险假通过与分层结果，不能只给整体一致率。

## 五、应用层评估

[Ragas 原论文](https://arxiv.org/abs/2309.15217) 分开评检索、证据使用与生成；reference-free 指标减少人工依赖，不意味不需要校准或证据。

| 链路 | 问题 | 示例失败 |
| --- | --- | --- |
| 检索 | 正确且有权限的证据是否进入上下文 | 相似但过期、正确版本未召回 |
| 生成 | 结论是否正确且证据支持 | 答对却引用无关、忠实复述错误材料 |
| 格式 | schema / 字段/约束是否合法 | 合法 JSON 但金额/单位错误 |
| Agent | 最终状态是否达成、动作是否授权 | 任务成功但重复扣款/泄露信息 |
| 服务 | 质量约束下的预算与 SLO | 只统计成功请求，隐藏超时和取消 |

构造 100 请求，60 个作答、其中 54 个正确、40 个拒答：作答覆盖率 60%，条件准确率 90%，已正确交付/全部请求为 54%。若只报 90%，系统可通过多拒答刷分；还应在可答/不可答子集分别计算误拒与正确拒答。不同风险任务权重需在看结果前声明。

## 六、评估驱动开发（线上闭环）

```
建初始评估集 ──► 上线 ──► 收集 bad case ──► 回流进评估集
     ▲                                        │
     └────── 每次改 prompt/模型/检索都跑回归 ◄──┘
```

图表示反馈关系；首次上线前仍需门禁与授权。回流样本需脱敏、去重、人工确认预期和知识版本；用于调参的回归集与未见验收集分开，不能不断看测试结果改配置。

样本量由风险、场景覆盖和希望识别的变化决定，没有统一“几十条够用”。离线先定位错误类别；线上 A/B 需明确随机化单位、时间窗、停机条件和质量/安全指标。用户留存或转人工率不能自证事实正确，流程变化也会影响它们。

## 七、微调/模型平台评估怎么接入上线门禁

| 变更 | 保持不变以形成对照 | 重点复验 |
| --- | --- | --- |
| prompt | 模型、数据、检索与预算 | 格式、任务回归与长度变化 |
| RAG | 问题、权限/知识快照 | 检索、引用、过期/无证据拒答 |
| LoRA/SFT | 模板、底座和测试题 | 目标收益、通用回归、挂载/卸载 |
| DPO/对齐 | 偏好数据隔离与裁判 | 长度匹配、误拒、危险假通过 |
| 服务/模型升级 | 请求负载、计时和成本口径 | 质量、SLO、取消/错误、工具兼容 |

### 门禁指标建议

门槛是业务决策，不是本页给出的普遍百分比。可用“核心任务允许退化 $\delta$、危险动作硬禁止、预算与超时有上限”的组合，提前定义统计方法、失败优先级和审批者。

构造同题 A/B：新模型多对 8 题、多错 5 题，只是观察净增 3 题；若新错题都来自高风险审批，总分上涨仍可能不可上线。按题配对分析，并单列强禁止事件，不把安全失败用语言质量均分抵消。

零失败不是零风险：对构造的 $n=100$ 个独立同分布试验，观察零失败，二项单侧 95% 上界解 $(1-p)^{100}=0.05$，得到 $p=1-0.05^{1/100}\approx2.95\%$。自适应攻击、同模板相关样本和新分布不满足此保证。不能据此给系统“认证安全”。

## 幻觉（Hallucination）

区分两个坐标：**与世界事实是否一致**、**给定证据是否支持**。忠实复述过期材料可能事实错误；正确答案配无关引用仍不满足证据要求。

| 情况 | 事实正确 | 证据支持 | 处理 |
| --- | --- | --- | --- |
| 正确版本政策 + 正确引用 | 是 | 是 | 仍检查完整性与权限 |
| 常识答对但引用不支持 | 是 | 否 | 不能通过引用忠实门禁 |
| 过期政策被准确复述 | 否（当前） | 是（该旧文） | 修证据版本与知识范围 |
| 无证据编出数字 | 待核/否 | 否 | 拒答或明确不确定，追查来源 |

### 成因

预训练主要学习文本分布，不直接提供实时事实 oracle；训练材料错误/过时、信息不足、证据冲突、上下文组织、奖励偏好与解码策略都可能影响结果。不能将所有幻觉唯一归于“概率生成本质”，也不能无证据宣称某模型因 RLHF 必然不愿承认未知。

### 检测

[SelfCheckGPT](https://arxiv.org/abs/2303.08896) 在特定人物文本设置中利用多次采样的不一致检测风险。**一致也可能共同错误，不一致也可能是有效多样答案**，它不是事实 oracle。token 概率/熵描述模型分布，不是经校准的“事实置信度”，高概率错误同样可能发生。

[FActScore](https://arxiv.org/abs/2305.14251) 将长回答拆为原子事实，判断可靠来源支持比例。借用这个思路的业务人工审计可记录：主张、证据片段/版本、支持/矛盾/不足、标注者及仲裁。构造五个主张中三支持、一矛盾、一不足，支持率为 3/5=60%；不能删去不足项后报 75%，也不能把剩余部分全叫事实错误。

### 缓解

| 手段 | 设计动机 | 仍需检查 |
| --- | --- | --- |
| RAG/联网 | 提供可更新证据 | 来源可信、时间/权限、注入与引用支持 |
| prompt/结构化输出 | 明确证据和拒答条件 | 合法格式不保证内容真实 |
| 低温度 | 减少部分采样波动 | 可能稳定输出同一个错误 |
| 诚实性/偏好训练 | 改善不确定与拒答行为 | 误拒、事实能力和新领域校准 |
| 人工复核 | 处理高风险/证据冲突 | 专家资质、工作量、版本和审计 |

工程目标是减少与发现错误，并让不可接受的动作不能执行；不承诺 RAG、CoT 或裁判能彻底消除幻觉。

## 高频追问

**pairwise 必然比 pointwise 可靠吗？** 不。它减少绝对尺度问题，却引入位置、平局/弃判和对手依赖；按任务做人工参照和交换顺序实验。

**从零搭评估先做什么？** 定任务/风险→建立版本化样本与参照→保存原输出/失败→分层判分→校准裁判→同预算配对对照→门禁/灰度。样本数和阈值不套统一模板。

**裁判一定要比模型强吗？** 看判断任务。格式可用 parser，事实可用可靠证据；推理判断也需要领域参照。模型“更强”不是精度校准的替代。
