# AI 安全合规与治理

> 大模型落地不只是技术问题，还要过「合规与治理」这一关——数据合规、内容安全、监管要求、伦理责任。这是企业级 AI 项目的红线，也是越来越被问到的方向。技术性攻防见 [大模型安全](/advanced/safety)，面试中如何把数据分类、外发、删除和取证落到系统设计，见 [LLM 数据分级、外发治理与审计证据面试题](/interview/data-governance-egress-audit-qna)；需要回答企业如何用资产台账、策略和审计账本统一治理时，见 [企业 AI 安全、合规与审计控制面系统设计面试题](/interview/enterprise-ai-governance-audit-system-design)。

## 一、安全 vs 合规 vs 治理

- **安全（Security）**：防越狱、防注入、防数据泄露等技术攻防（见 [大模型安全](/advanced/safety)）。
- **合规（Compliance）**：满足法律法规要求（数据保护、算法备案、内容审核）。
- **治理（Governance）**：组织内部的制度、流程、责任划分，确保 AI 被负责任地使用。

本文聚焦后两者，但治理不是「非技术」附录：它决定系统允许读写哪些资产、保存什么证据以及谁批准变更。本页面向 L3 的控制设计，不提供法律意见；法规适用必须由实际业务和法务按地区、时间与服务形态核实。

## 二、数据合规

数据是大模型的命脉，也是合规的高风险区：

- **处理依据与最小化**：记录数据用途、权限、处理依据、保留期与撤回路径。脱敏不是自动合法，合法来源也不意味着可用于任意训练目的；GDPR/PIPL 等的适用由法务确认。
- **数据来源合法**：训练数据的版权与授权（爬取的网页、书籍、代码许可证）——这是当前大量诉讼的焦点。
- **跨边界数据流**：列出模型API、日志、检索、遥测和供应商子处理链；本地部署仍可能因外部工具或监控外发，不由部署位置推断合规。
- **数据隔离**：多租户系统中严格隔离各租户数据（RAG 知识库尤其要做权限控制）。

## 三、内容安全与审核

生成式 AI 必须管控输出内容：

- **有害内容过滤**：暴力、违法、歧视、色情、危险操作指引等。
- **输入输出双向审核**：用规则 + 分类器 + 护栏模型（如 Llama Guard、各家 Moderation API）做二次审查。
- **行为政策**：明确产品支持/不支持的任务与风险类别，记录批准人；偏好训练只能改变行为倾向，不证明公平或无害，见 [RLHF](/finetuning/rlhf)。
- **未成年人保护、深度伪造（Deepfake）防范**：尤其语音克隆、换脸等高风险能力。

## 四、监管要求（中国视角）

不要把「用了大模型」直接等同某种备案义务。先记录公众/内部服务、提供者角色、能力与用途、个人信息及跨境数据流，再让法务核对对应条款、程序与适用日期：

- **备案与评估**：不能把算法备案、生成式服务相关程序和安全评估混成一个步骤；依据、触发条件和责任人分别核实。
- **生成内容标识**：核对实际适用的媒介、主体、显式/隐式要求与留存证据，不用一句「所有输出打标签」覆盖规则。
- **持续控制**：即使完成某项行政或评估程序，也不代表模型不会泄漏或越权；技术门禁仍须持续运行。

> GDPR、PIPL、AI Act 和中国生成式服务相关规则是法规检索入口，不是本页确认过的当前适用意见。本轮官方网页读取失败，未据此补写具体义务或生效时间；见文末边界。

## 五、可信 AI 的其他维度

- **可解释性**：区分用户可理解说明与机制证据；SAE、注意力图和生成理由不能自动证明因果或合规。
- **公平性**：定义群体、任务和测量指标，报告样本不足与冲突；总平均分可能掩盖少数群体退化。
- **可追溯（Accountability）**：出问题能追责，需日志审计、版本管理。
- **鲁棒性与可靠性**：对抗攻击下的稳定、幻觉的控制。

## 六、企业落地的治理实践

- **分级管控**：按场景风险分级（内部工具 vs 对外服务、辅助 vs 决策）施加不同管控。
- **Human-in-the-loop**：高风险决策保留人工审核。
- **最小审计证据**：记录必要的版本、授权、动作摘要和决定理由；原始 prompt/输出可能包含敏感信息，不应默认全量永久保存。
- **红队与持续监测**：上线前红队测试，上线后监控滥用与异常（见 [大模型安全](/advanced/safety)）。
- **责任划分**：明确数据、模型、应用各环节的责任主体。

## 七、面试专项：RAG/Agent 合规评审清单

企业面试里问“这个 AI 系统怎么过合规”，不要只说脱敏和审核，要给出可检查的证据链。

| 审查项 | RAG / Agent 要回答的问题 | 证据 |
| --- | --- | --- |
| 数据分级 | 哪些数据可进知识库、可出现在 prompt、可发给外部模型 | 数据分类表、模型通道白名单 |
| 授权来源 | 文档、日志、用户数据是否有合法来源和使用授权 | 数据源 owner、授权记录、版权说明 |
| 权限隔离 | tenant/user/role 是否贯穿检索、工具和缓存 | ACL 测试集、trace、越权拦截日志 |
| PII 处理 | 输入、检索结果、输出、日志是否脱敏 | 脱敏规则、抽检报告 |
| 数据出境 | 外部模型 API 是否接触敏感数据 | 路由策略、私有化通道、审批记录 |
| 保留期限 | prompt、trace、memory、评估样本保存多久 | retention policy、自动清理任务 |
| 删除链路 | 用户或文档删除后，向量、倒排、缓存、记忆是否同步删除 | 删除审计日志、回归测试 |
| 高危动作 | Agent 写操作是否经过人审、幂等、可回滚 | HITL 记录、业务单号、审计日志 |
| 安全评估 | 越狱、间接注入、数据泄露、误拒是否测试 | 红队报告、adversarial set 指标 |
| 责任归属 | 出问题谁负责、谁审批、谁回滚 | RACI、发布审批单、事故预案 |

### 合规面试答法

### 从清单走到执行证据

**构造事件**：用户撤回一份文档。只删除源库是不完整的：索引、缓存、对话记忆、离线评测副本和备份都要有生命周期策略。若文档曾进入模型权重，删除源文件不等于模型遗忘；需明确是否训练、能否停止使用派生产物以及风险升级路径。

每项控制记录四件事：责任人、执行位置、测试证据、例外批准。例如外发限制由网关执行，不只写在 system prompt；高危动作批准绑定用户、对象、参数与有效期，不给 Agent 永久授权。日志记录「批准了什么」而不是只有「有人点击确认」。

| 门禁 | 可观察证据 | 不能替代的判断 |
| --- | --- | --- |
| 检索ACL | 未授权样本零返回及缓存隔离测试 | 未知绕过路径与完整法务审查 |
| 外发路由 | 实际请求目的地、字段与批准记录 | 仅凭模型服务部署在内网 |
| 删除 | 源、索引、缓存与派生副本状态 | 参数记忆是否删除 |
| 版本变更 | 模型/工具/政策版本与回归结果 | 一次审计通过后永久有效 |

> 我会把 RAG/Agent 合规拆成数据、模型、工具、日志四层。数据层做分类、授权、ACL 和删除；模型层按敏感度路由到外部 API 或私有化模型；工具层做最小权限、人审、幂等和审计；日志层做脱敏、保留期和可追溯。上线前用权限测试集、注入对抗集、PII 抽检和高危动作演练作为证据，而不是口头保证。

## 八、高频追问

**Q：AI 安全和 AI 合规有什么区别？** 安全偏技术攻防（防越狱、注入、泄露）；合规偏法律法规（数据保护、内容审核、备案）；治理是组织层面的制度流程。落地大模型三者都要管，缺一不可。

**Q：企业用大模型的主要合规风险？** 数据隐私（PII、GDPR/PIPL）、训练数据版权、数据跨境、内容安全（有害/违规输出）、监管备案、多租户数据隔离。其中数据合规和内容安全是最常见的红线。

**Q：私有化就合规吗？** 不是。还要核查输入授权、工具和日志外发、运维权限、保留与删除；成本优势也需按实际负载测量。见 [AI 系统设计](/engineering/system-design)。

**Q：AI 生成内容标识怎样落实？** 先核实主体、媒介和适用规则，再定义标识、传播与检查链路；本页不代替当前法规解释。

**Q：怎么在产品里落地内容安全？** 输入输出双向审核（规则 + 分类器 + 护栏模型）、价值观对齐训练（RLHF）、高风险操作人工确认、滥用监控与红队测试、保留审计日志，多层防御并持续迭代。

**Q：RAG 系统的数据合规要注意什么？** 多租户严格数据隔离与权限控制（用户只能检索到有权访问的文档）、知识库数据来源合法授权、敏感信息脱敏、检索/回答可溯源、防间接 Prompt 注入导致的数据泄露。
