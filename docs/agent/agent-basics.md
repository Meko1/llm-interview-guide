# Agent 基础与框架

> **模型可以提议下一步，但不能自行授予权限或证明动作成功。** Agent 工程的目标不是自主性最大化，而是在明确边界内完成可检查的任务。

## 一、什么是 LLM Agent？ {#agent-definition}

<span id="工程定义-模型提议-执行器负责"></span><span id="一、什么是-llm-agent"></span><span id="十、面试加厚版-agent-的核心心智模型"></span>

本页采用工程定义：系统在任务过程中，由模型根据目标和观察结果选择下一步行动，并通过工具执行、更新状态、继续决策或结束。不同产品对 Agent 的命名并不一致；应描述实际控制流，而非用名称判断能力。

普通问答主要产生回答；RAG 增加证据检索；Agent 还会决定下一步行动。RAG 可以是 Agent 的只读工具，但一次固定检索加生成不必包装成自主 Agent。

**行动意图不等于执行事实。** 模型输出 send_email，只能说明它提出了调用；是否获准、是否发送、发送给谁，都应由执行器与业务系统确认。

## 二、核心组件与责任分离 {#agent-architecture}

<span id="二、四大核心组件"></span><span id="_2-1-规划-planning"></span><span id="_2-2-记忆-memory"></span><span id="_2-3-工具使用-tool-use"></span><span id="_2-4-行动-action"></span><span id="二十、agent-生产化架构"></span><span id="_20-1-orchestrator-做什么"></span><span id="_20-2-tool-executor-做什么"></span><span id="_20-3-policy-层做什么"></span>

```text
用户任务 → 编排器读取状态 → 模型提出行动意图
                           ↓
                    参数、身份、策略与预算校验
                           ↓
               只读执行 / 写入审批 → 工具执行器
                           ↓
                外部业务结果 → 持久化状态与观察
                           ↓
                    再决策 / 暂停 / 终止
```

| 组件 | 负责什么 | 不应该负责什么 |
| --- | --- | --- |
| 模型 | 分解任务、选择工具、解释结果 | 授予权限、确认账务事实 |
| 编排器 | 转移状态、调度、预算与停止 | 用自然语言替代业务约束 |
| 策略与审批 | 判断操作是否允许、是否需确认 | 只接受模型自报风险级别 |
| 工具执行器 | 校验契约、执行、记录结果与操作 ID | 把超时一律当成未执行 |
| 状态与审计 | 恢复任务、追踪决策和副作用 | 无限保留明文敏感数据 |

长期记忆、多 Agent 和复杂规划不是必选件。先把上述责任边界做清楚，再按任务添加能力。

## 三、经典范式与自主性取舍 {#agent-choices}

<span id="自主性取舍-越动态-不一定越合适"></span><span id="三、经典范式-react"></span><span id="七、主流框架"></span><span id="十一、agent-和工作流到底怎么区分"></span>

| 方式 | 下一步由谁决定 | 适用条件 | 主要代价 |
| --- | --- | --- | --- |
| 固定工作流 | 开发者定义节点与分支 | 流程稳定、规则明确 | 需维护异常分支 |
| 路由或受限 Agent | 模型在允许集合中选择 | 输入多样，但动作边界清楚 | 误路由、工具选择错误 |
| ReAct 式循环 | 根据观察迭代选择行动 | 下一步依赖检索或环境反馈 | 循环、错误累积、成本 |
| Plan-and-Execute | 先计划，再执行与修订 | 多步骤任务可拆分 | 计划陈旧、修订与恢复成本 |

ReAct 论文研究了交错推理与行动的范式，不能据此保证任意工具环境都可靠。生产观测记录可见行动、状态变化和校验结果；不要求服务暴露或保存模型私有思维链。

固定流程也能包含模型节点和复杂分支；Agent 也可被状态图强约束。不要简单说“工作流没有智能”“Agent 一定更不稳定”。在同一任务与预算下比较实际完成率、风险与维护代价。

框架可以提供状态、工具和追踪接口，但不能代替权限、幂等与评测设计。选型时验证可恢复行为、审批语义、版本治理和部署约束，不用框架排行榜替代任务分析。

## 四、Agent 的控制循环 {#agent-loop}

<span id="四、agent-的控制循环"></span><span id="十二、agent-loop-怎么设计"></span><span id="_12-1-状态里应该放什么"></span><span id="_12-2-终止条件怎么设计"></span><span id="二十八、agent-运行时预算"></span>

状态至少保存任务目标、用户约束、任务与步骤 ID、业务对象版本、已完成操作、观察摘要、预算、审批记录和最终结果。聊天历史不是唯一状态源；业务执行事实应来自业务系统或操作账本。

| 状态 | 可以发生什么 | 应记录什么 |
| --- | --- | --- |
| READY | 请求模型提出下一步 | 模型、Prompt、工具契约版本 |
| VALIDATING | 检查结构、权限、业务条件和预算 | 拒绝原因或待审批动作快照 |
| AWAITING_APPROVAL | 暂停，不执行该写操作 | 审批人、期限、对象和参数摘要 |
| EXECUTING | 执行已获准动作 | operation_id、尝试次数、截止时间 |
| RECONCILING | 调用结果未知，查询外部状态 | 查询结果与恢复依据 |
| COMPLETED / FAILED / CANCELLED | 输出结果或限制 | 已完成、未完成和未知的操作 |

这是教学状态模型，不是某个框架的完整 API。每次状态转移要能说明：谁触发、依据是什么、是否可能重复、怎么恢复。

**预算要在模型外部限制。** 设置最大步数、总时长、模型 token、工具次数与费用上限；预算既包含失败重试，也包含并行子任务。先做调用前预留，再按实际消耗结算，避免并发任务各自通过检查却共同超支。

重复检测不能只比工具名；需要考虑规范化参数、业务对象和是否获得新证据。预算耗尽时报告部分完成，不能自动扩大权限或继续写入。用户取消也不代表正在进行的外部动作已经被撤销。

## 五、规划、观察与终止 {#agent-planning}

<span id="五、规划范式概览"></span><span id="十六、planning-计划为什么经常错"></span><span id="_16-1-任务收缩"></span><span id="_16-2-显式计划模板"></span><span id="_16-3-计划审查"></span>

把“帮我处理客户问题”收缩为明确目标、允许工具、交付结果和不可接受错误。计划中写出预期观察与停止条件，不把一份生成计划当作真实世界已经满足的前提。

| 观察结果 | 后续策略 |
| --- | --- |
| 证据充分、目标已满足 | 校验并结束，不为凑步骤继续调用 |
| 资料缺少、用户意图歧义 | 澄清或转人工 |
| 工具输入被拒绝 | 依据错误修正参数，不直接重复 |
| 外部状态变化 | 重新校验条件，必要时重新审批 |
| 写操作结果未知 | 进入恢复查询，不重新规划同一写入 |

Reflection 或自我批评可以产生修订候选，但不能替代测试、事实核查或业务确认。一次“模型认为自己成功”不是停止条件；停止要绑定可观察结果。

## 六、工具契约：结构正确还不够 {#agent-tools}

<span id="十三、工具调用设计-agent-的手脚"></span><span id="_13-1-工具描述怎么写"></span><span id="_13-2-工具粒度怎么定"></span><span id="_13-3-工具参数为什么要校验"></span><span id="二十六、agent-工具调用的工程细节"></span><span id="_26-1-工具返回值怎么设计"></span><span id="_26-2-工具错误怎么反馈给模型"></span><span id="_26-3-幂等为什么重要"></span><span id="三十一、agent-与-mcp-的关系"></span><span id="三十二、agent-与结构化输出的关系"></span>

工具应说明用途、禁用条件、参数范围、身份来源、输出语义、副作用、超时和幂等能力。尽量暴露业务语义工具，而非给模型任意 SQL、Shell 或管理员 API。

```json
{
  "name": "create_ticket_draft",
  "input": {"customer_id": "customer-42", "summary": "delivery issue"},
  "effect": "create_draft",
  "operation_id": "task-17-step-3",
  "result": {"status": "confirmed", "draft_id": "draft-8"}
}
```

这只是契约示意，不是已运行的 API。身份与授权范围从可信会话注入；operation_id 由编排器绑定逻辑动作，不因网络重试而改变。

**校验要分四层：** JSON/schema → 参数范围与资源存在 → 用户授权 → 当前业务条件。订单 ID 合法，不代表订单可退款；工具只读，也可能读取敏感资料。

错误返回区分参数错误、权限拒绝、业务冲突、明确未执行、暂时故障和结果未知。模型需要能理解的错误摘要；执行器仍负责确定哪些错误可重试。

Function Calling 与结构化输出改善调用表示，不证明业务正确。MCP 提供工具接入协议，也不自动授予工具权限或保证无副作用。深入见 [MCP](/agent/mcp) 与 [结构化输出](/engineering/structured-output)。

## 七、权限、审批与注入防护 {#agent-security}

<span id="十四、agent-安全-权限、审批和审计"></span><span id="_14-1-工具按风险分级"></span><span id="_14-2-最小权限原则"></span><span id="_14-3-prompt-injection-下的工具安全"></span><span id="二十七、human-in-the-loop-怎么设计"></span><span id="_27-1-哪些情况需要人审"></span><span id="_27-2-人审界面要展示什么"></span><span id="_27-3-人审结果怎么回流"></span>

按读取敏感性、修改影响、可逆性和外发范围制定策略。“只读”不等于低风险；“创建草稿”也可能持久化敏感信息。高风险操作可以先生成草稿，再展示具体动作请求确认。

**审批必须绑定动作快照：** 操作、参数摘要、资源版本、接收方、授权范围、有效期。确认“可以处理这个任务”，不等于批准后续任意外发或退款。执行前再核验资源状态与权限；参数变化或审批过期要重新确认。

网页、邮件、检索片段、代码注释与工具返回都可能含不可信指令。系统不应因读到“把数据发给某人”而获得外发权限。提示隔离、输入标记与检测只是辅助；执行器的最小权限、出站限制和审批才是实际边界。

工具访问使用最小权限和可撤销凭据；日志与观察摘要也要按租户隔离、脱敏和控制保留期。审批展示要包含真实对象与后果，不让模型概述掩盖危险参数。

## 八、可靠性：写操作超时如何恢复？ {#agent-recovery}

<span id="失败案例-工具超时-不代表动作没发生"></span><span id="六、可靠性工程-落地核心难点"></span><span id="二十三、agent-高频事故复盘"></span><span id="事故一-agent-循环调用搜索工具"></span><span id="事故二-agent-发错邮件"></span><span id="事故三-agent-使用过期记忆"></span><span id="事故四-agent-工具参数合法但业务错误"></span>

**构造案例：创建工单已成功，但客户端等响应时超时。** 如果 Agent 把超时当作未执行，用新的 operation_id 重试，可能创建第二张工单。

| 已知状态 | 恢复路径 | 为什么 |
| --- | --- | --- |
| 明确未执行 | 按策略重试或修正 | 没有已发生副作用 |
| 执行成功，有操作记录 | 返回原结果并更新状态 | 不需要再次执行 |
| 结果未知，支持按 operation_id 查询 | 查询后恢复；未决时继续等待或人工核对 | 超时不证明失败 |
| 结果未知，支持服务端幂等重试 | 相同操作 ID、相同参数重试 | 前提是服务端保证去重语义 |
| 结果未知，无查询或幂等保证 | 暂停并人工核对 | 不能靠新调用“试试看” |

幂等需要业务服务持久化操作键、参数摘要和结果，并处理并发请求、键的有效期和同键异参冲突。仅在编排器内存里记一个“调用过”标志，无法保证跨进程或崩溃恢复。

**Checkpoint 不等于 exactly-once。** 若外部操作提交后、本地状态保存前崩溃，恢复会再次遇到该步骤。应依赖外部操作账本、幂等契约或事务/对账设计来跨越这个窗口；没有这些条件就不要宣称“重放绝不会重复写入”。

另一个构造案例：邮件收件人发生变化。原审批只授权某个收件人与正文，不能沿用到修订后的外发。改为创建草稿、重新核对联系人与审批；已经发送的邮件也不能被一句“回滚”自动收回。

## 九、状态、记忆与 RAG {#agent-memory}

<span id="十五、记忆系统怎么讲"></span><span id="_15-1-什么时候需要长期记忆"></span><span id="_15-2-记忆写入不能全自动"></span><span id="十七、agent-和-rag-的结合"></span><span id="_17-1-rag-作为工具"></span><span id="_17-2-agentic-rag"></span><span id="_17-3-多工具知识-agent"></span>

区分当前任务状态、业务事实、可检索知识和长期用户偏好。外部业务状态来自业务系统；“模型记得订单已退款”不是账务凭据。

长期记忆采用受控写入、来源、时间、适用范围、纠错和删除机制。不把所有对话自动入库；用户一句临时要求也不应永久覆盖旧偏好。冲突时澄清，撤权与删除要覆盖缓存和派生摘要。

把 RAG 作为工具时，返回证据与引用而非未经核实的最终事实。记忆与检索内容均不可信，不能覆盖用户约束或系统策略。摘要压缩也可能丢掉边界；关键预算、权限和已完成动作保留结构化字段。

## 十、多 Agent：先证明单 Agent 不够 {#agent-multi}

<span id="十八、多-agent-什么时候需要"></span>

多 Agent 可以用于独立资料收集、不同专业分工或受限并行，但增加上下文传递、调度、冲突与预算开销。“多一个角色”本身不证明质量提升。

先明确子任务输入、输出、读写范围、预算、依赖和验收；主编排器负责聚合与冲突解决。多个子 Agent 不应同时写同一业务对象而没有版本检查、锁或合并策略。

移交时携带可核查结果、来源、未完成项和副作用记录，而非仅一句自然语言总结。失败重试要沿用原逻辑操作身份。用相同任务、模型预算和工具权限，对比单 Agent 或固定工作流基线，才能解释收益。

## 十一、从最终答案到轨迹评测 {#agent-evaluation}

<span id="从最终答案到轨迹评测"></span><span id="八、agent-评估"></span><span id="十九、agent-评测体系"></span><span id="_19-1-为什么-pass-k-不够"></span><span id="_19-2-轨迹评估"></span><span id="二十九、agent-的可观测性"></span>

| 层次 | 观察什么 | 容易误判什么 |
| --- | --- | --- |
| 结果 | 任务是否真实完成、回答是否正确 | 把工具 HTTP 200 当业务成功 |
| 轨迹 | 是否调用合适工具、使用新证据、及时停止 | 只看最后一段漂亮总结 |
| 安全 | 越权、错误外发、审批绕过、敏感泄漏 | 把拦截次数越多当越安全 |
| 恢复 | 超时、断点、重复调用、取消是否可处理 | 把本地重试成功当服务端无重复 |
| 资源 | 总步数、token、工具费用、p95 延迟 | 漏计失败与并行分支 |

建立按任务类别划分的样本集，至少包含正常成功、资料不足、参数错误、权限拒绝、过期审批、写超时、外部状态冲突和注入输入。故障注入要检查真正的副作用次数，不只检查模型是否道歉。

评测器可以读取 trace 与业务结果，Judge 对主观质量评分；确定性约束用可执行规则检查。记录模型、Prompt、工具和状态图版本，固定基线与预算。人工抽查 Judge 不一致与安全边界样例，不把自动分数当作独立事实认证。

**重复试验与故障重试不是一个分母。** 同一任务从干净环境独立运行多次，用来测随机性和稳定性；一次运行内部的重试、恢复与人审仍属于该次运行，并计入成本和结果。对每题报告单次成功、至少一次成功和全部成功的区别，保留失败轨迹；不能挑最好一条 trace 代表上线可靠性。进一步见 [重复试验评测](/agent/repeated-trial-evaluation)。

<details>
<summary>L3 / L4 追问：规划与轨迹是否能解释收益？</summary>

减少工具次数不一定更好，可能只是提前放弃；增加步骤也不代表推理更深。比较任务完成、失败类别与单位成功任务成本，同时控制工具权限和时间预算。观察多个合理轨迹，而不是只接受一条参考调用顺序。

</details>

## 十二、生产架构与白板练习 {#agent-production}

<span id="二十一、agent-系统设计题模板"></span><span id="三十、agent-的灰度与发布"></span><span id="三十八、agent-现场白板题-设计一个客服-agent"></span><span id="三十九、agent-现场白板题-设计一个-coding-agent"></span>

以下是**模拟系统设计题**，不代表企业真题或已实施项目。

**客服 Agent：** 查询订单与政策 → 澄清意图 → 生成处理建议或草稿 → 当前业务条件核验 → 写动作审批 → 执行与对账。把退款与赔付限额交给规则系统，知识不足或结果未知时转人工。

**Coding Agent：** 限定工作区与工具 → 定位问题 → 提议修改 → 检查 diff → 运行允许的验证 → 报告结果。文件路径校验、凭据隔离、命令权限和不可信仓库内容都属于边界；测试通过不证明没有安全问题。

上线时同时版本化模型、Prompt、工具 schema、策略与状态图；支持限流、暂停、任务取消、灰度和失败对账。更新运行时前检查正在等待审批或恢复的旧任务如何迁移，不只验证新任务正常。

用户看到的失败说明要区分已完成、未完成和未知，提供任务 ID、下一步与人工入口。不能在外部动作状态未知时承诺“什么也没发生”。

<span id="九、高频追问"></span><span id="面试专项-agent-失败怎么排查"></span><span id="二十二、agent-项目怎么讲才像真实做过"></span><span id="二十四、面试前-5-分钟速记"></span><span id="二十五、agent-深挖追问-从-会做事-到-可上线"></span><span id="_25-1-为什么-agent-比普通-llm-更难上线"></span><span id="_25-2-agent-为什么需要状态图"></span><span id="_25-3-为什么说-agent-的上下文工程更难"></span><span id="三十四、agent-高频追问补充"></span><span id="三十五、agent-终极答题模板"></span><span id="三十六、agent-面试中的反面回答"></span><span id="_36-1-agent-就是大模型加工具"></span><span id="_36-2-让模型自己决定所有步骤"></span><span id="_36-3-工具参数用-function-calling-就安全了"></span><span id="_36-4-agent-失败就多重试几次"></span><span id="三十七、agent-简历项目描述模板"></span><span id="四十、agent-面试最后-20-问"></span><span id="四十一、agent-最终速记模板"></span><span id="四十二、agent-答题收口-三种时长版本"></span><span id="_30-秒版本"></span><span id="_2-分钟版本"></span><span id="_10-分钟版本"></span><span id="四十四、agent-最终检查清单"></span>

| 层级 | 模拟追问 | 回答应给出的证据 |
| --- | --- | --- |
| L0 / L1 | Agent 与普通工具调用有何区别？ | 谁决定下一步、是否有反馈闭环 |
| L1 | JSON 正确，为什么还不能执行？ | 授权、资源与业务状态校验 |
| L2 | 工具超时后能不能重试？ | 操作 ID、服务端契约、未知结果查询 |
| L2 | 审批后参数变化怎么办？ | 动作快照、有效期与重新审批 |
| L3 | ReAct 或规划为何改善任务？ | 同预算实验、失败轨迹与基线 |
| L4 | 多 Agent 是否值得？ | 并发收益、冲突、安全与完整成本 |

项目表达用一套结构即可：**任务边界 → 最简单方案 → 动态决策必要性 → 一次失败轨迹 → 修复与验证 → 未解决风险**。只实现 Demo 就写 Demo；不要把模拟工具、构造场景或未压测能力包装成生产履历。

自测：能否画出暂停与恢复？能否解释 HTTP 成功与业务成功的区别？能否防止审批后换收件人？能否说明 checkpoint 的重复副作用窗口？能否给出“不该用多 Agent”的反例？
