# Claude Code 子 Agent 与多 Agent 编排

> 若要把子 Agent 放进企业级控制面，系统回答上下文隔离、worktree、任务所有权、验证门禁和合并仲裁，见 [智能体运行时架构高频问答](/interview/agent-runtime-architecture-qna)。

> 2026-11-05 读取的[官方子 Agent 文档](https://code.claude.com/docs/en/sub-agents)说明：子 Agent 在独立上下文工作，也独立发起请求并计入用量。主 Agent 本身也可并行调用独立工具；子 Agent 的优势是职责和上下文分离，不是从“单线程”变成“多线程”的保证。

## 一、为什么需要子 Agent？

单 Agent 干复杂任务有两个硬伤：

1. **上下文污染**：一个子任务（如「读懂整个 auth 模块」）会产生海量中间内容，全灌进主上下文会迅速塞满、引入噪声、干扰主线。
2. **职责混杂**：探索、修改与验证共享同一对话时，容易把中间假设当成已确认事实。

子 Agent 同时解决这两点：**派生独立的子 Agent，各自有自己的上下文，并行处理，只回传结论。**

```
主 Agent（保持干净的主线上下文）
  ├─ 派生子 Agent A：调研 auth 模块 ──► 只回传「结论摘要」
  ├─ 派生子 Agent B：调研 payment 模块 ──► 只回传「结论摘要」
  └─ 汇总 A/B 的结论，继续主任务
```

这正是 [上下文工程](/agent/context-engineering) 的 **Isolate** 操作落地。

## 二、子 Agent 机制（Task / AgentTool）

- **派生**：本轮官方文档使用 Agent 工具；旧版 Task/AgentTool 名称不应当成固定 API。
- **独立上下文**：子 Agent 有自己的对话历史、自己的 token 预算，不共享主上下文。
- **工具继承/过滤**：子 Agent 可被限定只能用某些工具（最小权限、聚焦职责）。
- **同步/异步生命周期**：可阻塞等待子 Agent 结果，也可异步并行多个。
- **摘要回传**：主上下文通常接收结果摘要，但不要声称中间过程绝对不可查看。摘要要包含文件位置、执行结果、未核事项，主 Agent 仍需复核。

> 上下文隔离不等于权限、凭据或文件隔离。默认工作目录可能仍是同一仓库；需要独立工作区时，对照安装版本配置 `isolation: worktree`，并检查外部服务是否仍共享同一资源。

一次委派至少写清：目标、可读/可写路径、允许工具、交付物、停止条件与禁止事项。结果按“发现 / 修改 / 验证 / 未核”分开。例如只读审查返回 `file:line` 与风险，不把“建议修复”记成“已经修复”。

## 三、协调者 / 蜂群模式（Coordinator / Swarm）

以下是协作范式；产品中的 subagents、agent teams 与独立并行会话应按各自文档区分，而不是统称为同一个内部机制：

- **协调者模式（Coordinator）**：一个主 Agent 当「项目经理」，把大任务拆解成子任务、派发给多个 worker Agent、收集并整合结果。对应 [工作流](/agent/workflow) 的 Orchestrator-Workers。
- **蜂群/Agent Teams（Swarm）**：多个 Agent 组队协作，可能有更对等的分工。
- **通信**：设计上可使用消息队列或共享任务账本；是否存在特定 Mailbox 实现，本页不作源码事实断言。

这类模式适合**可并行分解**的大任务（如「给整个项目补测试」拆成按模块并行），但协调开销、子任务划分、结果整合都是难点（见 [多 Agent](/agent/multi-agent) 的取舍）。

## 四、Worktree 隔离：文件级并行的关键

多个 Agent 同时改同一个仓库会**互相踩踏**（改同一文件、git 冲突）。解法是 **Git worktree**：

- 每个 Agent 在**独立的 worktree**（同一仓库的独立工作目录 + 独立分支）里干活，文件互不干扰。
- 各自完成后再合并（merge）回主分支。
- 这让「多个 Agent 真正并行改代码」成为可能，而不是串行排队或互相覆盖。

> Worktree 只隔离检出的文件，通常仍共享 Git 对象，也不会自动隔离数据库、凭据或部署目标。同一工作区也可按互斥路径协作，但共享目录、格式化、生成产物与合并必须由单一协调者负责。

<details>
<summary>案例：两个 worker 都成功，为什么整合仍失败？</summary>

一个修改接口，另一个按旧接口修改调用方，各自局部检查通过。协调者应先锁定接口契约，再汇总补丁并运行跨模块检查；发生冲突时保留双方改动，由文件 owner 仲裁，不能用整文件覆盖或 reset 消除另一人的工作。

</details>

## 五、什么时候用、什么时候别用

| 场景 | 建议 |
| --- | --- |
| 任务可并行分解、子任务独立 | ✅ 多 Agent（并行加速 + 上下文隔离） |
| 单个子任务上下文很重（大量探索） | ✅ 子 Agent 隔离，保护主上下文 |
| 简单线性任务 | ❌ 单 Agent 就够，多 Agent 是过度设计 |
| 子任务强耦合、需频繁交互 | ⚠️ 协调开销可能大于收益 |

务实原则同 [工作流 vs Agent](/agent/workflow)：**别为了多 Agent 而多 Agent**——它带来协调成本和 token 开销，只在「并行收益 / 上下文隔离需求」明确时才值得。

## 高频追问

**Q：子 Agent 最大的价值是什么？**
上下文隔离。它把「会产生海量中间内容的子任务」外包出去，子 Agent 在自己的上下文里折腾、只回传结论，主 Agent 的上下文保持干净聚焦。这让主 Agent 能处理远超单上下文容量的复杂任务，而不被中间过程塞爆。

**Q：子 Agent 是为了更快还是为了省上下文？**
两者都有，但「省上下文（隔离）」往往是更核心的动机。并行能加速独立子任务；但即使串行，把重上下文的子任务隔离出去、只回传摘要，也能极大缓解主上下文压力。隔离价值常大于并行价值。

**Q：多个 Agent 同时改代码怎么不冲突？**
独立 worktree 降低工作时覆盖，但合并仍可能冲突。另一种方式是同一目录内锁定互斥路径，由主 Agent 独占共享文件和构建。无论哪种，都要记录任务所有权并在整合后验证，不能从 worker 的成功状态推断系统成功。

**Q：协调者模式和工作流的 Orchestrator-Workers 是一回事吗？**
本质相同：一个中心 Agent 拆任务、派发给多个 worker、整合结果。区别在 worker 是否是有独立上下文和工具的完整子 Agent。详见 [工作流 vs Agent](/agent/workflow) 和 [多 Agent](/agent/multi-agent)。

**Q：什么时候不该用多 Agent？**
简单线性任务（单 Agent 足够，多 Agent 是过度设计）、子任务强耦合需频繁交互（协调开销大于并行收益）、对成本敏感（多 Agent 的 token 消耗显著更高）。先用最简单的单 Agent，确实遇到「上下文塞爆」或「明显可并行」才上多 Agent。
