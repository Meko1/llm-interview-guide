# Claude Code 工具系统详解

> 工具（Tools）是编程 Agent 的「手脚」——模型的能力边界由它能调用的工具决定。这一页详解 Claude Code 的工具系统：工具如何定义/注册/调用、各类核心工具的设计要点、以及任务管理的双轨架构。架构见 [代码架构](/claude-code/architecture)，机制见 [核心机制](/claude-code/mechanisms)。

## 一、工具的本质：模型输出意图，框架执行

再次强调这个关键认知：**模型不直接执行任何操作**。它只输出结构化的「工具调用」——`{工具名, 参数}`，框架负责：查注册表 → 校验参数 → 权限检查 → 真正执行 → 把结果回喂模型。底层走 [Function Calling](/agent/function-calling-mcp)。

一个工具的定义通常包含：

| 字段 | 作用 |
| --- | --- |
| name | 工具名（模型据此调用） |
| description | 说明何时使用；模型还受用户目标、历史、权限与其他指令影响 |
| input schema | 参数的 JSON Schema（约束 + 校验） |
| 执行函数 | 真正干活的逻辑 |
| 权限要求 | 是否只读、是否需要确认 |

> 工具描述写得好不好，直接决定模型用不用对、用没用错——这是工具设计的第一性原则。

## 二、文件操作工具（Read / Edit / Write）

编程 Agent 最高频的工具，设计上有几个讲究：

- **Read**：按行读取、支持分段（大文件不一次性灌爆上下文）、记录「已读」状态。
- **Edit**：用**「旧文本 → 新文本」的精确替换**，而非整文件覆盖——更安全（只改该改的）、diff 清晰、不易误删。要求 old_string 唯一匹配，否则报错让模型重试。
- **Write**：新建或替换文件。原子写入和崩溃一致性是实现问题，本页未核验，不能当作产品保证。
- **并发修改**：编辑前读过不代表内容永远新鲜；另一个 worker 可在读取后改写。失败时重读并合并，不要绕过唯一匹配检查强行覆盖。

## 三、搜索与导航工具（Glob / Grep）

这是 [agentic search](/engineering/coding-agent-internals) 的基础——让模型像人一样自己探索代码库：

- **Glob**：按文件名模式找文件（`**/*.ts`），快速定位。
- **Grep**：按内容正则搜索代码，基于 **ripgrep**（极快），支持按文件类型、上下文行数过滤。
- 价值：检索当前可访问文件，无需预建语义索引。结果仍受忽略规则、查询范围、编码、截断与并发写入影响；无命中不等于全库不存在。符号引用与语义检索可补充文本搜索，两者不是非此即彼。

## 四、命令执行工具（Bash）

最强大也最危险的工具——能跑任意 shell 命令：

- **只读检测**：解析命令判断是否有副作用（`ls`/`cat` 只读 vs `rm`/`git push` 有副作用），只读命令可放宽权限。
- **命令解析**：风险检查需理解复合命令和间接执行；具体是否采用某个解析库未核验，解析成功也不证明命令无副作用。
- **输出截断**：长输出（如全量测试日志）截断/摘要，防止吃爆上下文。
- **超时控制**：防止命令挂死。
- 权限上它是重点管控对象（见 [核心机制 - 权限](/claude-code/mechanisms)）。

## 五、任务管理：TodoWrite vs Task 双轨

复杂任务需要区分“跟踪待办”和“委派工作”。2026-11-05 读取的[官方工具表](https://code.claude.com/docs/en/tools-reference)与[子 Agent 文档](https://code.claude.com/docs/en/sub-agents)使用 Agent 等现行名称；原稿的 TodoWrite / Task 双轨是旧版概括，不是稳定存储契约：

| | 任务跟踪 | 子 Agent 委派 |
| --- | --- | --- |
| 存储 | 按当前实现与会话配置核对 | 独立上下文不保证任意跨会话恢复 |
| 用途 | 给当前任务列待办、跟踪进度 | 派发独立子任务给子 Agent |
| 上下文 | 共享主上下文 | **独立上下文**（隔离） |
| 适合 | 单 Agent 的多步骤清单 | 需要隔离/并行的复杂子任务 |

任务状态表示工作流进度，不能证明测试或修改已完成；子 Agent 结果需附证据，见[子 Agent 与多 Agent](/claude-code/subagents)。

## 六、工具调用的工程细节

- **并行调用**：模型一次可发起多个**相互独立**的工具调用（如同时 grep 几个关键词、读几个文件），框架并发执行、一起回传，省往返延迟。
- **结果回喂**：工具结果作为新消息加入上下文，模型据此决定下一步。
- **失败处理**：保留足够诊断信息，同时脱敏。参数错误可纠正；权限拒绝不应换入口绕行；执行超时可能已产生副作用，应先核对结果再重试。
- **结果体积控制**：大结果截断 + 提示「已截断，可分页读取」，平衡信息量与上下文成本。

## 高频追问

**Q：Edit 工具为什么用「旧文本→新文本」而不是整文件覆盖？**
更安全、更精确：只改该改的部分，避免模型「重写整个文件」时误删或改坏无关代码；diff 清晰可审查；要求 old_string 唯一匹配，强制模型基于真实内容定位，减少幻觉式修改。整文件覆盖只在新建或彻底重写时用 Write。

**Q：为什么 Bash 工具要做只读检测和 AST 解析？**
为了权限和安全：区分只读命令（`ls`/`grep`，可放宽自动执行）和有副作用命令（`rm`/`git push`，需确认/拦截）；AST 解析能更准地理解复合命令结构、识别危险操作，避免简单字符串匹配被绕过。

**Q：TodoWrite 和 Task 有什么区别？**
这是旧版名称下常见的概念区分。当前应按实际工具定义识别任务跟踪与 Agent 委派，不能从名称推断持久化、恢复或隔离保证。

**Q：为什么搜索用 grep 而不是 embedding 检索？**
文本搜索适合已知符号与字符串，语义搜索适合描述性需求，代码导航适合引用关系。先看任务类型，再检查范围、索引新鲜度与结果截断；不能宣称一种搜索对所有任务更可靠。

**Q：工具结果太长会怎样？**
可能截断、摘要或返回分页提示。下一步应缩小查询或读剩余范围；未见全文就只能报告部分证据。窗口容量取决于模型配置，不固定为 200K。

<summary>追问：shell 超时后可以原样重跑吗？</summary>

先确定命令是否已产生副作用：文件编辑看 diff，外部提交查业务 ID，后台进程查存活状态。只读失败与“提交结果未知”必须分开。重试预算、幂等键与权限由执行层控制，不由模型的一句“再试一次”决定。
