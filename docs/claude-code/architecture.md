# Claude Code 代码架构

> 这页专注 Claude Code 的分层；横向比较 Claude Code、Codex、OpenClaw、Hermes 的任务运行时与可迁移设计原则，见 [智能体运行时架构高频问答](/interview/agent-runtime-architecture-qna)。

> 本页的分层图是用于理解与自研的**概念模型，不是 Claude Code 私有源码结构图**。2026-11-05 读取的[官方运行原理](https://code.claude.com/docs/en/how-claude-code-works)明确解释了模型、工具、上下文和任务循环，但不据此推断内部类名、缓存实现或依赖库。功能见[总览](/claude-code/overview)，行为见[核心机制](/claude-code/mechanisms)。

> 原稿的 QueryEngine、MicroCompact、React/Ink 等实现说法缺少可复核版本证据，本页不将它们当成现行实现事实。

## 一、分层架构全景

理解编程 Agent 时，可以按以下职责拆分（同一实现未必物理分层）：

```
┌─────────────────────────────────────────────┐
│ 入口层 (CLI)        启动、参数解析、运行时初始化   │
├─────────────────────────────────────────────┤
│ 交互层 (REPL)       输入、流式展示、审批与中断    │
├─────────────────────────────────────────────┤
│ 编排层 (Orchestrator)                        │
│                     回合生命周期、token 预算、    │
│                     上下文压缩触发、会话持久化     │
├─────────────────────────────────────────────┤
│ Agentic Loop 核心   组织上下文→调 API→解析工具    │
│                     调用→权限检查→执行→递归       │
├─────────────────────────────────────────────┤
│ 工具执行层          文件/命令/搜索/任务/子 Agent  │
├─────────────────────────────────────────────┤
│ 通信层              流式 HTTP，多后端适配         │
│                     (Anthropic/Bedrock/Vertex) │
└─────────────────────────────────────────────┘
              ↕ 横切：权限、Hooks、MCP、配置、遥测
```

图中表达职责而非严格依赖顺序：权限需在实际执行前检查，取消信号需跨层传播，工具结果又会回到上下文。仅画出层次不能证明实现可靠。

## 二、各层职责详解

### 入口层（CLI）

负责进程启动：解析命令行参数（交互模式 / `-p` 管道模式 / 各种 flag）、初始化运行时、加载配置与项目记忆。终端 Agent 的「main 函数」。

### 交互层（REPL）

负责接收输入、展示流式输出、权限询问与中断状态。自研时需要区分“模型正在生成”“工具正在执行”“等待批准”，避免界面已经取消而后台工具仍继续写入。具体 UI 技术栈不影响这一契约。

### 编排层（Orchestrator / QueryEngine）

整个会话的「指挥中枢」：

- 管理多轮对话的**回合生命周期**；
- 维护 **token 预算**，依据所选模型和配置决定何时缩减上下文；
- 触发**上下文压缩**（compaction）；
- **会话持久化**（把对话记成 JSONL transcript，支持恢复、成本追踪）。

### Agentic Loop 核心

决策引擎，整个系统的心脏（详见 [核心机制](/claude-code/mechanisms)）：组织上下文 → 调模型 API → 解析模型返回的工具调用 → 权限检查 → 执行工具 → 把结果喂回 → 再调，循环至完成。支持**并行工具执行**、流式、错误恢复。

### 工具执行层

把模型的「意图」变成「真实操作」：

| 工具类 | 代表 | 要点 |
| --- | --- | --- |
| 文件操作 | Read / Edit / Write | 编辑前重读；检测内容变化与替换歧义 |
| 搜索导航 | Glob / Grep | 标明范围与截断，不能把无命中当成全库不存在 |
| 命令执行 | Shell 工具 | 超时、进程终止、凭据与工作目录边界 |
| 任务管理 | 当前版本任务工具 | 状态与证据分开，勾选不代表验证通过 |
| 子 Agent | Agent | 独立上下文；工作区隔离另行配置 |

### 通信层

流式 HTTP 调用模型 API，封装多后端适配（Anthropic / Bedrock / Vertex 等），处理 SSE token 流、重试、鉴权。

## 三、横切关注点（贯穿各层）

- **权限系统**：Allow/Ask/Deny 三级 + 多层规则优先级，插在「工具执行前」（见 [核心机制 - 权限](/claude-code/mechanisms)）。
- **Hooks**：在工具调用前后等生命周期点注入用户脚本，可拦截/校验。
- **MCP**：通过 [MCP 协议](/agent/mcp) 接入外部工具，内置 + 外部多种传输。
- **配置系统**：用户级 / 项目级 / 企业级配置合并；项目记忆 CLAUDE.md。
- **观测**：自研系统应记录模型调用、工具结果、拒绝原因与取消状态；日志脱敏、留存与数据出口需单独治理，不能假设产品默认替你完成。

## 四、为什么这样设计？（架构动机）

| 设计 | 解决的问题 |
| --- | --- |
| 分层 + 单一职责 | 复杂 Agent 可维护、可测试、可替换组件 |
| 编排层独立于 Loop | token 预算/压缩/持久化和决策逻辑解耦 |
| 工具层抽象统一 | 新增工具只需注册，模型用同一套调用协议 |
| 多后端适配层 | 一套代码对接不同模型供应商 |
| 横切的权限/Hooks | 安全和工程约束不侵入业务逻辑 |

这是一套参考设计。验收时沿一次调用检查：用户授权是否绑定具体任务与工作区，工具是否收到同一取消信号，失败是否区分“未执行”和“执行结果未知”，最终回复是否附可复核的 diff 与命令结果。模型自述“完成”不能替代这些证据。

## 高频追问

**Q：Claude Code 为什么用 React/Ink 做终端 UI？**
这一实现前提在本轮未核验，不能据此回答产品选型。作为设计讨论，声明式组件可组织流式输出、审批与任务状态；但应以具体版本源码或官方说明证明采用了哪种库。

**Q：编排层（QueryEngine）和 Agentic Loop 是一回事吗？**
概念上可分：Loop 管下一步决策与工具反馈，编排管预算、生命周期、持久化与恢复。这不证明产品里存在名为 QueryEngine 的公开组件；面试应讲职责和失败边界，而不是背未经核验的内部名称。

**Q：工具是怎么接进来的？**
工具有统一的类型定义和注册机制；每个工具声明名称、参数 schema、执行逻辑、权限要求。模型通过 Function Calling 输出「调用哪个工具+参数」，框架查注册表、校验权限、执行、回传结果。新增工具只要按协议注册即可，模型不用改。

**Q：这套架构对我自己做 Agent 有什么借鉴？**
关键经验：① 把「单步决策的 loop」和「会话级编排（预算/压缩/持久化）」分层；② 工具用统一注册+调用协议；③ 权限/Hooks 作为横切关注点插在执行前，不污染主逻辑；④ 通信层抽象多后端。这些是任何生产级 Agent 都要面对的工程问题。
