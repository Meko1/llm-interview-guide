# MoE 训练与专家并行

> DeepSeek-V3、Qwen-MoE、Mixtral 把 MoE 推成了主流架构，「MoE 怎么训、怎么并行、怎么保证专家负载均衡」成了训练岗的高频深挖点。本文承接 [MoE 混合专家模型](/basics/moe) 的架构介绍，聚焦**工程侧**：路由与负载均衡、辅助损失、容量因子与 token 丢弃、专家并行（EP）与 AllToAll 通信、DeepSeekMoE 的细粒度+共享专家设计。并行通信基础见 [AI 训练集群与网络通信](/pretraining/ai-infra-networking)。

## 面试先背这几句话

- MoE 用**稀疏激活**换「大参数量、小激活算力」：总参数很大，但每个 token 只激活 Top-K 个专家。
- 训练最大难题是**负载均衡**：路由器容易把 token 都送给少数专家，导致「专家坍缩」，其余专家训不到。
- 解决靠**辅助损失（auxiliary/load-balancing loss）** 或 **无辅助损失的偏置调整（DeepSeek 的 aux-loss-free）**。
- 专家并行（EP）把不同专家放到不同 GPU，token 路由靠 **AllToAll** 通信——这是 MoE 特有且易成瓶颈的通信模式。
- DeepSeekMoE 两个关键设计：**细粒度专家**（切更小更多）+ **共享专家**（每个 token 都过，学通用知识）。

## 一、MoE 训练为什么特殊

稠密模型每个 token 走全部参数；MoE 每个 token 只走 Top-K 专家（如 8 选 2）。这带来三个训练特有问题：

1. **路由是离散/不可导的**：选哪个专家是 argmax/TopK，梯度不能直接穿过「选择」这个动作——靠对被选专家的 gating 权重加权来间接回传。
2. **负载不均衡**：路由器是学出来的，训练早期容易形成「马太效应」——热门专家越来越热，冷门专家收不到 token、学不到东西、进一步没人选，最终**专家坍缩**。
3. **通信模式变了**：专家分布在不同卡上时，token 要被「发到对应专家所在的卡、算完再收回来」，引入 AllToAll。

## 二、路由与负载均衡 ★

### 2.1 路由器（Router / Gating）

对每个 token，router 是一个小的线性层 + softmax，输出对各专家的分数，选 Top-K：

$$g = \text{softmax}(x \cdot W_g), \quad \text{选 TopK 专家，按 } g \text{ 加权求和输出}$$

### 2.2 负载均衡损失（Auxiliary Loss）

经典方案（GShard/Switch Transformer）：加一个辅助损失，惩罚「token 分配不均」。直觉是让**每个专家被选的比例**和**分给它的路由概率**都趋于均匀：

$$L_{aux} = \alpha \cdot N \cdot \sum_{i=1}^{N} f_i \cdot P_i$$

这是 top-1 风格的定义：$f_i$ 是实际分配占比（和为 1），$P_i$ 是 softmax 概率均值（和为 1），N 是专家数；均匀分配时损失为 $\alpha$，不是 0。Top-K 的计数可按 `K×token 数` 归一化，也有其他缩放约定，移植公式前必须核对实现。$\alpha$ 太大可能伤任务质量，太小可能压不住不均衡。

### 2.3 无辅助损失均衡（DeepSeek aux-loss-free）★

DeepSeek-V3 主要以每专家动态偏置做 batch 级均衡：过载调低、欠载调高。**偏置只改变 Top-K 选择，专家输出的 gating 权重仍来自原始 affinity score**。报告同时保留了很小的序列级均衡辅助损失，因此 aux-loss-free 不能译成整个模型完全没有辅助损失。其消融支持特定配方中的改善，不保证任何模型都不会损伤质量。

### 2.4 容量因子与 token 丢弃

- **专家容量（capacity）**：若 T 个 token、E 个路由专家、每 token 选 K 个专家，则均匀平均分配数为 `T×K/E`；容量常取 `ceil(容量因子×T×K/E)`，具体还可能对齐 kernel 块大小。
- **token 丢弃（dropping）**：超出容量的 token 被丢弃（不经该专家，走残差直连）。容量因子小 → 丢得多、省算力但伤质量；大 → 少丢但浪费算力和显存。
- dropping、padding 与 dropless 是不同策略。DeepSeek-V3 报告其训练和推理均不丢 token；不能把容量因子+丢弃当成所有 MoE 的必选实现。

构造 T=4096、E=8、K=2、容量因子 1.25 时，平均每专家 1024 份路由分配，容量 1280。若某专家收到 1500 份，容量型实现有 220 份溢出；一个 token 可能仍保留另一专家分支，不必然整个 token 被跳过。dropless 实现则需承受不均衡峰值，而非假设无成本。

## 三、专家并行（Expert Parallelism, EP）★

当专家太多放不进一张卡时，把**不同专家分到不同 GPU**：

```
token 在各卡上产生 → 按路由结果 AllToAll 分发到专家所在卡
                   → 各卡专家计算
                   → AllToAll 收回到原来的卡 → 继续后续层
```

- **两次 AllToAll**：一次分发（dispatch）、一次收集（combine）。这是 MoE 训练/推理的**特有通信开销**，token 越多、专家越分散，通信越重。
- **和其他并行组合**：EP 常和 DP/TP/PP 组成复杂的多维并行。EP 通信量大，通常也希望放在高带宽域内。
- **负载不均的连锁反应**：如果专家负载不均，热门专家所在卡成为瓶颈，其他卡空等——所以负载均衡不仅关乎质量，也直接影响 EP 的吞吐（木桶效应）。

> 面试点：**MoE 的 AllToAll 和稠密模型的 AllReduce 是不同通信原语**；MoE 训练把「计算省下来的钱」部分花在了「通信」上，工程上要靠通信-计算重叠、分组路由等手段抵消。

## 四、DeepSeekMoE 的关键设计

DeepSeekMoE 的两个设计方向（见 [DeepSeek 专题](/models/deepseek)）：

1. **细粒度专家（Fine-grained）**：把专家切得更小、数量更多，Top-K 也更大。好处是专家组合数爆炸增长，**专业化程度更高、知识分得更细**。
2. **共享专家（Shared Expert）**：设置 1~2 个**所有 token 都必过**的共享专家，负责学「通用/共性知识」，让路由专家专注差异化知识，减少冗余。

配合 aux-loss-free 均衡、MLA 压 KV Cache，构成了 DeepSeek-V3 的高性价比配方。

## 五、MoE 的推理与部署挑战

- **显存 vs 算力错配**：常驻部署需要保存全部专家权重，但可分片/卸载；每 token 激活少不保证便宜，瓶颈可能是内存、通信或小专家 GEMM，需按负载实测。
- **批处理下的专家利用**：一个 batch 里 token 被路由到各专家，专家利用率取决于 batch 内 token 分布；小 batch 时很多专家「空转」。
- **EP 推理**：大 MoE 推理也用专家并行 + AllToAll，vLLM/SGLang 等已支持（见 [推理框架对比](/inference/serving-frameworks)）。
- **量化**：MoE 权重量化收益大（省显存），但要注意专家间敏感度差异。

## 六、常见坑与调参经验

- ❌ 辅助损失权重过大 → 为了均衡牺牲质量；过小 → 专家坍缩。要监控**专家负载分布**这个指标。
- ❌ 容量因子设置不当 → 丢 token 太多或显存爆。
- ❌ 忽视 router 的训练稳定性 → 早期路由抖动大，可用 router z-loss 稳定 logits。
- ❌ EP 通信没和计算重叠 → AllToAll 成为吞吐瓶颈。
- ✅ 监控每个专家的 token 命中数、路由熵，及时发现坍缩。

## 高频追问

1. **MoE 相比稠密模型省的是什么？代价是什么？** 省的是激活算力（每 token 只走 Top-K 专家），代价是显存（参数全量加载）和通信（AllToAll）以及训练不稳定（负载均衡）。
2. **什么是专家坍缩，怎么解决？** 路由马太效应导致少数专家垄断 token、其余训不到；解决靠负载均衡辅助损失，或 DeepSeek 的无辅助损失偏置调整。
3. **负载均衡辅助损失怎么起作用？** 惩罚 token 分配比例与路由概率的不均匀，鼓励各专家被均匀选择；权重 α 是质量与均衡的权衡。
4. **DeepSeek 的 aux-loss-free 是什么？** 用每专家可调偏置控制选择，gating 不加偏置；V3 仍保留序列级辅助均衡项，不能说完全无辅助损失。
5. **专家并行的通信是什么？和稠密模型有何不同？** EP 用两次 AllToAll 分发/收集 token，稠密模型是 AllReduce 同步梯度；AllToAll 是 MoE 特有瓶颈。
6. **容量因子和 token 丢弃是什么？** 每专家有处理上限（容量因子×平均负载），超出的 token 被丢弃走残差；是吞吐/显存与质量的权衡。
7. **DeepSeekMoE 的细粒度专家和共享专家分别解决什么？** 细粒度提升专业化与组合表达力；共享专家承载通用知识、减少路由专家的冗余。
8. **MoE 部署为什么贵？** 参数全量占显存但激活少，显存/多卡成本高，且小 batch 时专家利用率低、AllToAll 通信开销大。

## 路由排障与状态恢复

同时记录每层每专家的路由份数（注明按 token 还是 Top-K 分配）、最大/平均负载、overflow/drop 比例、router logits、gating 熵和 dispatch/combine 耗时。全局平均均衡仍可能掩盖单序列或单 rank 热点；聚合前先保留切片。

恢复不仅保存专家和优化器，还要保存 router、动态均衡偏置与更新计数、RNG、数据游标。更改 EP/DP 布局后核对专家 ID 映射与分片加载，否则“权重能加载”仍可能把专家装错位置。

事实边界依据 [DeepSeek-V3 v2 第 2.1.2 节](https://arxiv.org/html/2412.19437v2#S2.SS1.SSS2)：偏置、序列辅助项、节点限制和不丢 token 都是该报告配方；其他框架支持需按实际版本核对。
