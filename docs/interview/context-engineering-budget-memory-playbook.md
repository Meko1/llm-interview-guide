# Context Engineering：上下文预算、压缩与记忆检索系统设计

> Agent 的上下文不是聊天记录拼接。它是有限 token 预算内，由系统策略、当前任务、工具状态、检索证据、长期记忆和历史摘要组成的动态工作集；塞得越多不一定越聪明，反而可能更慢、更贵、更容易被污染。

## 一、30 秒面试回答

我会为每次运行建立 context budget，而不是无限累积消息。系统策略和安全约束固定保留；当前任务、工具状态和已授权证据按优先级分配预算；历史对话做结构化摘要，长期记忆通过权限过滤和相关性检索按需注入。每个上下文片段带来源、时间、租户、置信度和 token 成本，超预算时按明确策略压缩、淘汰或请求澄清。摘要与记忆也视为不可信派生数据，防止错误信息或注入指令跨会话持续存在。trace 记录最终 context manifest，才能回放“为什么模型看到了这些内容”。

## 二、上下文分层与预算

| 层 | 内容 | 策略 |
| --- | --- | --- |
| 不可替代 | 系统安全、工具边界、任务契约 | 固定预算，不被摘要覆盖 |
| 当前工作集 | 用户目标、状态、最近工具结果 | 高优先级、短生命周期 |
| 检索证据 | RAG 文档、代码、网页 | ACL 过滤、引用与去噪 |
| 会话历史 | 已确认偏好、决策、未完成事项 | 摘要 + 最近窗口 |
| 长期记忆 | 跨会话事实与偏好 | 按需检索、可撤销 |

预算按模型/接口窗口、输出预留、任务风险和成本制定；最大输入、最大输出和推理token是否共享窗口需按提供方合约核对。不能用中文字符数或另一个模型的tokenizer估算生产硬上限，最终计数应覆盖消息封装、工具Schema、图像/附件和其他接口开销。

构造共享窗口例，单位均为目标tokenizer的token而非字符：W=32,768，预留输出4,096、封装估计512、安全余量1,024；系统/工具定义3,072、任务/权威状态2,048、历史摘要2,048、已授权记忆1,024，固定输入共8,192。可用证据预算为32,768-4,096-512-1,024-8,192=18,944。30个各800token的候选共24,000，超过5,056；若片段等长最多23个，但仍要按引用覆盖、冲突与版本选择，不随机丢弃金额或授权条件。真实封装开销不是固定512，此数仅演示预留逻辑。

固定指令本身超过硬上限时应拒绝组装/改用经评测且允许的模型，不静默裁掉安全要求。输入、工具步数、deadline和花费分别限额：token未超不代表成本/时延未超；多Agent共用父任务原子预留，返回usage后结算，unknown调用不立刻释放全部额度。

## 三、压缩不是简单摘要

| 方法 | 适合 | 风险 |
| --- | --- | --- |
| 最近窗口 | 短对话连续性 | 丢失早期关键决定 |
| 结构化摘要 | 任务进度、约束、已验证事实 | 摘要幻觉或遗漏 |
| 分层摘要 | 长会话与周期性 checkpoint | 需要版本与重建策略 |
| 检索历史 | 大量历史记录 | 需要权限与相关性过滤 |
| 任务状态外置 | 工具参数、计划、审批状态 | 不能让模型文本成为唯一事实 |

摘要分“用户声明、已验证事实、决策、未决事项、来源和验证状态”；模型自报置信度不作校准概率。每条指向可复核原文或权威状态，保留否定词、金额单位、有效期与未完成动作。高风险审批/订单/工具结果从业务服务读取，不从摘要恢复。

失败例：原记录为“用户希望退款100元，审批待处理，渠道提交后响应丢失”，摘要写成“已批准并退款100元”，会同时伪造授权和完成状态。状态字段应保持 approval=pending、effect=unknown，并先按operation_id查账。摘要失真时回到原证据重新构建，不能继续摘要旧摘要让错误固化；原来源不可读则降为待核，不用记忆补造事实。

## 四、记忆检索与污染控制

长期记忆写入前要做权限、来源、有效期和冲突检查；读取时按 tenant、用户、角色与任务相关性过滤。外部文档、工具输出和用户话术不能因“被写进 memory”就取得系统指令优先级。对低置信、过期或冲突记忆，应显示不确定性、重新验证或不注入。

删除、撤权和偏好变更要能定位 memory、摘要、缓存和索引并主动失效。跨租户或跨用户复用记忆属于严重隔离事故。

## 五、观测与评测

manifest记录片段ID、来源、版本、token、优先级、摘要血缘、检索分数、纳入/排除原因和输出引用；“已纳入”或“被引用”不证明内部决策实际使用，更不证明结论正确。按授权范围保存摘要/哈希而非默认完整prompt。指标分母分别定义：摘要错误条数/抽检命题数、过期注入数/所有注入记忆数、满足质量与预算的完成任务数/请求数；超长、冲突、撤权、注入、预算耗尽和全无证据题单列。

### 5.1 预算控制面与确定性降级瀑布

预算不只是输入 token 上限，还包括输出预留、时延、成本、最大工具步数和各来源配额。定义软/硬阈值，并让降级顺序可预测：先去重和裁剪低价值工具输出，再压缩历史，再减少检索候选，随后请求澄清或将任务转异步；高风险操作在证据不足时直接拒绝执行。不要在预算耗尽后随机丢掉系统约束或授权证据。

### 5.2 记忆生命周期与删除收敛

生命周期可有 `candidate -> quarantined -> verified -> active -> superseded -> tombstoned -> erased`，也应允许隔离后直接删除，而非强制所有状态逐个走过。verified是内容审核，active还需要有权启用；常规召回只允许active且当前ACL有效。撤权/删除先发布tombstone和revision，再异步清理索引、缓存、摘要；旧checkpoint恢复和迟到写入必须检查revision，防止重新复活。已组装上下文/在途生成、备份和依法保留审计分别规定处理范围，不能声称删除一个向量即完成全系统抹除。

### 5.3 多 Agent 并发写与污点传播

共享记忆使用版本/CAS、租约或事件追加，明确冲突合并与删除优先规则；CAS只保护单次存储更新，不使跨索引清理变成事务。trust label保存在可检索元数据/血缘表，不能假定embedding本身可靠编码安全标签。`untrusted`摘要默认仍不可信，审核产生独立证明而非改文本前缀；执行器始终重验ACL和资源授权。来源撤销可按血缘隔离派生内容，血缘遗漏时不承诺完全追净。

### 5.4 上下文因果评测

不只报召回段数。消融时固定模型/工具/语料、数据划分与采样预算，用等长替代控制删除引起的位置/长度变化；重复比较任务成功、引用支持、风险动作和成本，不能把一次答案变化当作内部推理因果证明。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)本轮仅读作者摘要摘录：多文档QA和key-value检索对证据位置敏感；这是特定任务/模型的实验结果，不推出所有模型都必然忽略中间内容。

构造价值比较：加入800token记忆后，100个固定任务正确完成由70到72，但新增2次陈旧授权使用。质量平均上升不能抵消安全门禁失败；也需要重复试验判断2题变化是否稳定。证据未足够时采用澄清/只读或转人工，不能为了缓存命中保留撤销授权。

缓存替代方案需分开：前缀KV复用只减少部分重复计算，不保证答案正确；语义答案缓存则必须绑定授权域、知识/策略版本并重验当前权限。稳定系统/工具部分与动态记忆分区组织可能提高复用，但以固定提供方接口验证。[OpenAI Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching)本轮未取得可核正文，仅linked_only，不列未核的阈值、TTL或收益倍数。

## 六、高频问答

**Q：上下文越长越好吗？**

不是。长度可增加prefill工作与陈旧/无关内容，但“稀释注意力”不是所有模型质量必降的证明。比较同任务的短/长证据、位置和预算，保留输出空间，按问题选摘要、检索或权威状态外置。

**Q：如何避免摘要把错误永久带入后续会话？**

摘要带来源和版本，只把已验证事实写入长期层；高风险业务状态从权威系统读取；对摘要做定期重建、冲突检测和抽样评测，且允许删除/撤销。

**Q：记忆与 RAG 有什么区别？**

RAG 面向外部知识证据，通常按文档和权限检索；记忆面向用户/任务持续状态与偏好。两者都需检索、版本和 ACL，但写入规则、保留期和错误代价不同。

## 七、项目讲法模板

下面是假设性架构表达，未实现或未实测时改称“拟设计”。manifest支持复核输入，不能保证跨版本逐token复现；本轮没有压缩、缓存或隐私删除实验。

> 我们将 Agent 上下文拆为系统策略、当前状态、授权证据、历史摘要和长期记忆，并对每层分配 token 预算。工具和审批状态外置到权威服务，摘要只保留带来源的已确认信息；记忆读写均做租户、权限、有效期和污染检查。每次运行保存 context manifest，用于回放、成本分析和 bad case 定位。这样既控制了长上下文成本，也降低了陈旧记忆与间接注入跨会话放大的风险。
