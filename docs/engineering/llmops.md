# LLMOps：大模型应用的生产运营

> LLMOps 要回答三类运行问题：哪次变更改变了行为，成本上升发生在哪一跳，失败如何进入可复核的回归集。本文是运营设计建议，不承诺某套工具在固定时间内覆盖固定比例价值。

## LLMOps 和 MLOps 的区别（必考）

| 维度 | 传统 MLOps | LLMOps |
| --- | --- | --- |
| 模型来源 | 自己训练、版本化模型 | 多用 API/开源基座，**很少从零训** |
| 「代码」是什么 | 特征工程 + 模型代码 | **Prompt、RAG 配置、工具定义也是代码**，要版本化 |
| 评估 | 任务数据与指标，可有随机性 | 任务验收、轨迹、安全，judge 需校准并抽样人审 |
| 成本模型 | 依工作负载看训练、服务和数据成本 | API 用量或自部署容量、人审与重试综合计入，不必线性增长 |
| 失败模式 | 数值漂移、特征腐烂 | 幻觉、注入、跑偏、上游模型悄悄变更 |
| 迭代单元 | 重训模型（周/月） | 改 prompt/检索/路由（小时/天） |

## 生命周期全景

```
开发期            发布期             运行期             反馈期
评估集建设   ──►  影子流量/灰度  ──►  监控+护栏+成本  ──►  bad case 回流
prompt/RAG 调优    A/B 实验           告警与降级          评估集扩充/微调数据
     ▲                                                       │
     └───────────────────── 数据飞轮 ◄───────────────────────┘
```

核心思想：**评估驱动 + 闭环**。没有评估集的 LLM 应用 = 没有测试的代码（评估方法详见 [模型评估](/evaluation/evaluation)）。

## Prompt 工程化管理

- **版本化**：prompt 与代码分离存储（配置中心/专门平台），带版本号，可 diff、可回滚——「prompt 上线后发现变笨了」必须能一键回到上一版。
- **回归测试**：每次改 prompt 跑评估集对比，CI 里挡住「改好了 A 场景、改坏了 B 场景」的隐性回归。
- **环境隔离**：dev/staging/prod 的 prompt 独立发布，与代码发布同等纪律。
- **上游模型变更管理**：API 模型升级/微调版本切换都可能改变行为，切换前全量跑评估集，灰度放量。

## 监控：三层指标体系

| 层 | 指标 | 用途 |
| --- | --- | --- |
| **系统层** | TTFT、整体延迟、错误/超时率、token 用量与成本 | 和传统服务监控同构，按链路归因 |
| **质量层** | LLM judge 抽样评分、幻觉/忠实度、拒答率、工具调用成功率、护栏拦截率 | LLM 特有，靠抽样 + 自动评估 |
| **业务层** | 任务解决率、转人工率、用户点踩率、留存 | 最终裁判 |

实施时按阶段记录版本、用量、延迟与脱敏摘要，不默认收集所有 prompt。judge 样本按任务、租户风险和失败类型分层，固定抽样率不是通用最优值；保留人审一致性检查。告警同时看绝对预算、变化率和最小样本量，低基数的翻倍可能只是噪声。trace 传播见[Java 生产架构](/interview/java-ai-production-architecture-system-design)。

## 成本治理

成本失控是 LLM 应用最常见的生产事故，抓手按性价比排序：

1. **缓存**：前缀缓存（稳定 system prompt，见 [上下文工程](/agent/context-engineering)）+ 精确/语义缓存（重复问题直接回答）；
2. **模型路由**：简单请求走小模型，复杂才上旗舰（分级路由，见 [SLM](/models/slm)）；
3. **上下文瘦身**：历史压缩、检索 top-k 控制、工具结果截断；
4. **输出控制**：max_tokens 上限、要求简洁、结构化输出省废话；
5. **批处理**：按供应商实际价格与完成时限评估离线 API，不默认半价；
6. **预算与熔断**：按用户/租户设 token 配额，异常调用熔断——防止循环 Agent 烧穿预算。

## 发布与可靠性

- **灰度发布**：按风险和统计样本确定流量比例，固定版本并预置停止条件。影子流量禁用真实写工具或使用隔离副本，不能为了对比模型重复发信、扣款或建单。
- **降级链**：主模型超时/失败 → 备用模型 → 缓存答案 → 兜底话术；多供应商容错。
- **护栏（Guardrails）**：输入侧注入检测/敏感词，输出侧内容审核/PII 过滤/格式校验，Agent 侧步数与权限限制（见 [大模型安全](/advanced/safety)）。

## 数据飞轮：把 bad case 变成资产

```
线上交互 ──► 采集（点踩/低分/转人工/护栏命中） ──► 人工标注归因
                                                    │
  微调数据集 ◄── 高质量问答对沉淀 ◄── 修复验证 ◄── 加入评估集
```

- 每个 bad case 归因到环节（检索没召回？prompt 歧义？模型能力？）再修，不要上来就改 prompt；
- 评估集随业务演化持续扩充，这是团队最值钱的资产之一；
- 积累的优质交互数据后续可用于 SFT/DPO（见 [微调工具链](/finetuning/training-frameworks)），形成「越用越好」的飞轮。

回流前核对许可、PII、租户授权和数据驻留。用于优化的样本与最终验收集分离；点踩不一定代表模型错，点赞也不证明事实正确，必须归因。持续积累只提供改进机会，不保证自动越用越好。

## 上线前检查清单（面试可直接背）

1. 评估集与基线分数（质量有数）
2. 全链路 trace 与三层监控告警（出事能看见）
3. prompt 版本化与回滚方案（改坏能回退）
4. 成本预算、配额与熔断（钱有上限）
5. 降级链与多供应商容错（挂了有兜底）
6. 输入输出护栏与权限边界（安全有闸门）
7. bad case 回流通道（问题能变资产）

## 高频追问

**Q：LLMOps 和 MLOps 最大的区别？**
迭代单元变了：MLOps 围绕「重训模型」，LLMOps 围绕「改 prompt/检索/路由配置」——快但同样危险，所以 prompt 要像代码一样版本化、测试、灰度；同时评估从确定性指标变成「评估集 + judge + 人评」的组合。

**Q：线上怎么发现「模型变笨了」？**
分层告警：质量层（judge 抽样分、拒答率、工具成功率）突变 + 业务层（点踩率、转人工率）趋势 + 主动哨兵（定时跑固定评估集对比基线）。只靠用户投诉发现 = 已经晚了。

**Q：成本突然翻倍，怎么排查？**
按归因链查：trace 按链路/租户聚合 token 用量 → 定位是调用量涨（业务/滥用/Agent 死循环）还是单次变贵（上下文膨胀、缓存命中率跌、路由失效全走了大模型）。预防靠配额 + 熔断 + 缓存命中率监控。

**Q：prompt 变更怎么安全上线？**
评估集回归（挡隐性回归）→ 影子流量对比（高风险改动）→ 灰度放量盯指标 → 可一键回滚。核心观念：**prompt 就是代码**，享受同等的发布纪律。

**Q：怎么从零搭一个最小可用的 LLMOps？**
先选一个业务切片：版本化配置、覆盖核心成功和失败路径的评估集、脱敏 trace、费用账本、告警与回滚演练。样本数和周期由业务分布决定，不承诺一周或覆盖 80%。验收至少能从一条失败 trace 还原版本与错误阶段，并证明回滚后新请求使用旧配置。
