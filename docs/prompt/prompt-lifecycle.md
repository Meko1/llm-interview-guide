# Prompt 生命周期、实验与发布（PromptOps）

在线上系统里，Prompt 不是一段散落在代码中的字符串，而是一项会影响质量、成本、安全、工具行为和用户体验的**可发布资产**。改一条例子、一个变量默认值、一个模型参数，甚至一个工具 schema，都可能改变线上行为。因此 PromptOps 的目标不是“更快改提示词”，而是让每一次变更可复现、可评测、可灰度、可回滚、可审计。

本页是 Prompt 主栏目中的生产化主路径。它讲资产生命周期和控制面；“如何自动找到更优 Prompt”见 [自动化优化与 Prompt Ops](/prompt/prompt-optimization)，评测方法见 [模型评估与幻觉](/evaluation/evaluation)，发布门禁和线上实验的面试深问见 [LLM 评测与发布门禁实战](/interview/evaluation-release-gates)、[LLM 线上评测与灰度实验](/interview/online-evaluation-rollout-operations) 与 [PromptOps 模板治理与实验回滚](/interview/promptops-production-governance-playbook)。

## 一、为什么 Prompt 需要像代码一样治理

Prompt 直接影响输出，依赖模型、知识库与工具，效果又有非确定性。问题不是“存在数据库就不专业”，而是只保存可变文本、没有修订记录和运行依赖时，容易遇到：

- 不知道线上某个回答到底使用了哪版系统提示、few-shot 和变量。
- 修改温度、工具描述或 RAG 上下文后，无法解释为什么质量变化。
- 离线分数提高但核心客户退化，无法快速回退到完整可工作的组合。
- 同一会话在新旧模板间跳变，导致上下文格式不一致。
- 把密钥、用户数据、实验草稿直接写进 Prompt，形成安全和审计风险。

一句话定义：**PromptOps = 将 Prompt 及其运行依赖作为版本化配置，放进测试、发布、观测与回滚闭环。**

## 二、Prompt 资产到底包含什么

一个“版本”不能只是一段 `system_prompt`。建议把可影响行为的配置收敛到资产清单：

```yaml
prompt_id: customer_support_answer
version: 2026.07.20.3
template: templates/customer_support.jinja
variables_schema: schemas/support-input.json
few_shot_set: support-golden-v12
model_policy: chat-main-v5
decoding: { temperature: 0.2, max_tokens: 700 }
tools: [order_lookup@3, refund_preview@2]
rag_policy: support-index@2026-07-18
safety_policy: support-guardrail@7
eval_suite: support-release@21
```

以上 YAML 为资产清单示意，日期、路径和版本号是构造值，不是本项目已部署配置。将这些内容记录为不可变 `release_manifest`，定位“哪份模板、哪个模型、哪套索引和工具契约”共同作用于一次请求。

**别把追溯性等同于确定性复现。** 清单可重建配置，但还需当时的输入、实际检索片段、工具观察、路由结果与输出记录；即便齐全，远端服务也可能非确定或已不提供旧模型。不能锁定快照的依赖应明确标记，并通过回归和漂移监控控制风险，不能承诺每次重放逐字一致。

**版本规则。** 模板正文、变量 schema、few-shot、模型/解码参数、工具 schema、RAG/安全策略任一改变，都应形成新的可追踪 revision。是否让它们共享同一个语义版本号可按团队习惯决定，但 trace 必须能关联到完整 manifest。

还要区分三种标识：

| 标识 | 作用 | 风险 |
| --- | --- | --- |
| `prompt_id` | 标识同一任务资产 | 不能唯一定位一次发布 |
| `revision` / 内容摘要 | 定位不可变内容与依赖组合 | 仍不包含动态工具数据 |
| `production` 等 alias | 指向当前推荐 revision | 指针可以移动，不是可复现身份 |

[MLflow Prompt Registry 官方文档](https://mlflow.org/docs/latest/genai/prompt-registry/) 明确区分不可变 prompt version 与 alias，并提供按具体版本加载的方式。无论是否采用该平台，都应在请求开始时把 alias 解析为具体 revision，再把实际解析结果写入 trace；不要仅记录“用了 production”。动态模型路由同样记录实际命中的模型，不只记录策略名。

## 三、环境、渲染与密钥边界

典型环境为 `dev -> staging -> production`，环境之间不应只差一个模型 URL：

| 环境 | 主要目的 | 数据与权限 |
| --- | --- | --- |
| dev | 模板开发、lint、变量样例 | 合成或脱敏数据，低权限工具 |
| staging | 端到端集成、沙箱工具、回归 | 受控样本，禁止真实写副作用 |
| production | 灰度与正式流量 | 最小权限、审计与稳定分桶 |

渲染前检查变量 schema、必填项和默认值；渲染后检查实际 token、敏感字段和引用完整性。缺少订单号应返回未知或追问，不能由模板默认值补成一个“看起来合理”的真实订单。变量值按数据传入，不允许它重新定义模板语法；模板 sandbox 与模型的指令安全是两条不同边界。

渲染哈希和受控脱敏快照可帮助定位差异，但哈希不等于匿名化：低熵内容可能被枚举猜测。原文只在授权、加密、留存期限和审计条件下保存，普通日志不写用户秘密；不可重放的隐私数据应明确留出证据边界。

配置也要分层：稳定的资产存版本库/配置库，环境差异走受控参数，机密走 secret manager。把生产密钥拼进模板既不利于审计，也会扩大提示注入的影响面。

**一个 token 预算账本。** 构造有效上下文上限 8,192 token、输出预留 1,024 token，则输入上限 7,168。若系统规则 1,200、会话历史 1,500、工具 schema 500、检索片段 3,600，输入合计 6,800，剩余 $7,168-6,800=368$ token。消息包装和未计入字段也消耗预算，需用所选模型的计数方式在渲染后复核；字符数不是 token 数。

溢出时先按策略压缩/移除低优先级历史与片段，保留规则和必需证据，再重新计数。若关键证据仍放不下，分段处理或明确失败；不要从末尾静默截断导致引用和审批语义残缺。推理服务的输出/内部推理预算是否共享，需另查实际 API，不能直接套这个构造账本。

## 四、离线评测：发布前先证明没有明显退化

Prompt 变更的最小发布单元不是“文本改好了”，而是“新 manifest 通过了与任务相称的离线证据”。建议将评测集分成：

| 集合 | 作用 |
| --- | --- |
| golden | 业务最重要、答案或事实可核验的样本 |
| regression | 历史事故、用户投诉、已修复 bad case |
| boundary | 长输入、空字段、冲突约束、多语言等边界 |
| adversarial | 注入、越权、诱导泄露与格式攻击 |
| holdout | 不参与日常调参，用于防止过拟合 |

上述是用途分类，不自动保证数据互斥。调参可看 development 与已知 regression；最终验收 holdout 不返回给优化器。来自同一用户、文档或问题的近重复样本应成组划分；多次用 holdout 选方案后，它就成为开发集，应重新准备独立验收集。

评测同时看正确性、格式、引用/工具、安全、延迟和费用。关键切片与红线必须预先写进门禁；不是“总体分数提高就可豁免越权”。评测中没有观察到安全问题，也不是安全证明。

对于非确定性输出，固定一次随机种子并不足够。可重复运行、用 win/tie/lose 对比或置信区间观察，避免将随机波动误判成 Prompt 改进。

构造 200 条配对样本：旧版对 184 条，新版对 190 条，表面提升 3 个百分点。进一步记录“旧错新对”12 条、“旧对新错”6 条，净增 $(12-6)/200=3\%$；不能只说“修好12条”。重复试次、标签争议和高风险退化仍需检查，单次 200 条结果不足以宣称统计显著或全域更好。

## 五、发布门禁：从分数到允许上线的决定

将门禁分成三类会更清晰：

1. **硬门禁**：安全违规、数据越权、工具 schema 不兼容、关键格式失败，任一命中即阻断。
2. **预算门禁**：P95 延迟、平均/尾部 token、缓存命中和单位成本不可超过约定阈值。
3. **质量门禁**：主指标提升或不退化，关键切片不低于基线，低样本指标标记不确定而非强行判赢。

质量/预算确有业务豁免时，记录审批人、范围、有效期与停止指标；数据越权和违法操作不靠实验豁免获得授权。门禁还应检查测试与 production 工具能力差异，避免沙箱从未覆盖真正的副作用路径。

## 六、从 Shadow 到 Canary，再到 A/B

离线通过并不等于可以全量。线上实验需要先定义假设、主指标、护栏、停止条件和受众：

```text
shadow  : 复制请求给新版本，只记录结果，不影响用户
canary  : 小比例真实用户实际看到新版本，可随时停止
A/B     : 稳定分桶对照，比较预先定义的业务指标
ramp-up : 通过每一阶段门槛后逐步扩大比例
```

Shadow 候选不能携带真实写能力；执行器强制路由到模拟器、sandbox 或只提议不执行，不能仅在 prompt 里写“这是测试”。只读调用也有数据权限、网络出站、费用和限流影响。模拟工具返回无法完整代表生产行为，因此 shadow 是受限证据，不是全副作用验收。

按影响范围选择稳定分桶单元：单会话状态用 `conversation_id`，跨会话共享记忆可能需按用户或租户分桶；混桶会造成实验相互污染。标识使用受控伪名而非原始身份。分配时固定具体 manifest，恢复时不重新按当前 alias 随机切换；安全策略和资源权限仍每次重查，不随会话“粘住旧授权”。

**预算与实验效用分开算。** 构造每天 10,000 个请求，5% shadow 复制 500 次，每次候选输入 3,000、输出 500 token，增加输入 1.5M、输出 0.25M token。若假设单价分别为 2 与 8 元/M token，额外费用为 $1.5\times2+0.25\times8=5$ 元/天；这是虚构单价、不含工具、重试与缓存折扣，不是供应商报价。非复制型 A/B 不一定多一次调用，不能沿用 shadow 的“额外500次”账本。

Canary 主要观察故障/护栏，A/B 才按预定义随机化与指标比较效用；两者不是同义词。记录曝光分母、超时与丢失反馈，转化延迟未到期前不判胜。频繁看分数就停止需专门的序贯规则，不能随意选一个最高时刻宣布显著。

## 七、回滚的对象是完整 manifest，不是一段文本

回滚恢复的是一个仍可用、兼容的历史组合，而不是机械恢复所有旧值。模板、模型路由、few-shot、工具和索引需验证兼容；**已经撤销的权限、已修复的安全策略或数据删除要求不能跟着降级**。旧模型已下线或旧索引已销毁时，完整历史 manifest 只能用于追溯，不能假装可直接运行；发布前预先验好回退目标。

回滚控制面至少支持：按版本一键回退、按租户/场景回退、停止实验、冻结进一步发布、保留证据包。回滚后仍要检查会话粘性、缓存污染和进行中的长任务；不能假设修改配置后所有请求立即消失。

把对象分三类恢复：新请求切到已验证旧 revision；进行中任务保留版本记录，按兼容性选择完成、暂停或重新规划；已发生副作用走业务补偿/对账。**发出的邮件、已扣的款不会因为回滚 prompt 自动撤回**。超时不清楚是否完成时标记 `unknown_effect`，先查业务 operation ID，再决定是否重试。

缓存键至少覆盖影响输出的 revision、输入、租户/权限域和相关检索版本；若安全状态改变，缓存命中前仍核验读取权限。迁移 alias 也要核对所有进程实际解析的 revision、配置传播和缓存，不能把控制面显示“回滚成功”当成所有请求已切回的证据。清理不能误删其他租户可用数据。

## 八、观测与可追溯性

每条 trace 应关联：

```text
prompt_id + revision + rendered_prompt_hash
release_manifest_id + model/decoding policy
retrieval/index/tool/safety versions
experiment_bucket + conversation_id + tenant
usage, latency, finish_reason, feedback and policy events
```

这样才能回答线上排障的关键问题：“这个错误是否只出现在某个 Prompt revision？是否只影响某个模型路由、某个知识库版本或某个实验桶？”没有版本关联的用户点赞/差评很难成为可行动证据。

区分“模型生成完成”“工具提交”“业务已确认完成”。同一个 trace 记录请求/业务操作/重试的关联 ID，避免把重试重复计为独立成功；脱敏文本用于诊断，不能充当真实业务提交凭证。

bad case 回流前应经过脱敏、去重、授权和人工复核，再进入 regression 集。否则生产日志可能把敏感数据、攻击样本或偶然噪声直接变成后续优化的污染源。

## 九、一个轻量的交付流水线

```text
author -> lint/render -> local eval -> review
       -> staging integration -> release manifest
       -> offline gate -> shadow -> canary -> A/B ramp
       -> observe -> promote / rollback -> bad-case regression
```

小团队不需要第一天就构建复杂平台。可以从 Git 管理模板、CI 跑小型 regression、人工审批灰度、在日志中记录版本号开始；随着应用增多，再建设模板目录、评测服务、实验分桶、门禁和审计控制面。关键是先建立可复现的“版本 -> 证据 -> 发布”链条。

实际交付应附一个最小证据包：具体 manifest 与变更原因、独立评测版本及逐题差异、工具兼容检查、灰度受众/停止条件、回退目标可用性，以及进行中任务和未知副作用的处理负责人。本文流程是设计建议，未搭建 registry、CI 或灰度实验。

## 十、面试高频问答

### Q1：为什么 Prompt 版本不能只存一段文本？

文本之外还有变量、示例、模型、工具和动态观察。manifest 关联完整依赖组合，但不能保证远端输出逐字一致；另保留受控运行证据和不能重放的边界。

### Q2：改 `temperature` 或工具 schema 算 Prompt 变更吗？

它们都可能改变生成行为和工具执行结果，因此至少必须形成新的可追踪 release revision。是否与模板使用同一版本号是实现选择，但 trace 与门禁必须看到这个变化。

### Q3：离线分数提升，为什么不能直接全量？

离线样本和生产分布不同，工具/会话状态也不同；shadow 需先隔离副作用，再观察候选行为，不能靠一次 dry-run 证明真实写安全。canary 观察护栏，A/B 比较预先定义的业务效用。

### Q4：某关键租户退化但全局平均提升，是否扩量？

不应仅靠全局平均决定。先检查该租户是否属于受保护切片、样本量是否足够、退化是否越过护栏；必要时按租户回退或停止实验。企业产品的正确性常常是分层约束，不是总平均最大化。

### Q5：回滚后如何确认没有遗留问题？

从实际 trace 确认新请求命中目标 revision，核对缓存、存量任务和未知效果。保留当前授权与安全修复；已经提交的业务操作需对账或补偿。回滚是受控发布，不是撤销现实世界的按钮。

### Q6：PromptOps 和 LLMOps 的关系？

PromptOps 是 LLMOps 的一个资产维度，聚焦提示模板、实验与发布；LLMOps 还覆盖模型、RAG、工具、观测、成本和运行治理。二者共享评测、发布和审计基础设施，但边界不同。

## 十一、60 秒面试收束

> 我把提示及依赖登记为不可变 manifest，请求记录 alias 实际解析的 revision 和动态观察。渲染后核 token，离线看质量、安全、预算与关键切片；shadow 强制隔离副作用，canary 看护栏，A/B 按稳定分桶比较效用。回滚切换到仍可用的兼容组合，不恢复已撤销权限，也不声称撤回已发生动作；存量任务、缓存和未知效果分别对账。发布证据与脱敏 bad case 形成下一轮回归，而不是用一张平均分替代上线判断。

<details>
<summary>L1：一次线上回答如何定位到提示版本？</summary>

关联 prompt ID、具体 revision、manifest、实际模型和渲染摘要；不要只记 production alias。缺哪些动态输入会影响复现，也要说清。
</details>

<details>
<summary>L2：新版更准但超时增加，应怎样发布或回退？</summary>

同时检查质量/尾延迟门禁、关键切片和业务预算；先定义 canary 停止条件，核对配置传播与存量任务。回退不降低当前安全策略，未知工具效果先对账，不通过重跑 prompt 盲目补偿。
</details>

<details>
<summary>L3：200条配对样本净增6条，能证明新版更好吗？</summary>

不能直接宣称。核对12条修好与6条退化的切片和标签，估计逐题配对及多次试验的不确定性；数据不泄漏、实验分桶不污染，最终验收集独立，线上停止规则预先规定。
</details>
