# 自动化提示优化与提示工程化（Prompt Ops）

> 自动优化不是让模型替你想一句更漂亮的话，而是在明确任务与预算内搜索候选，获得可信反馈，再决定是否替换基线。它能放大有效评估，也能更快地过拟合或“钻指标空子”。本文聚焦搜索与验收；完整资产发布链见 [Prompt 生命周期](/prompt/prompt-lifecycle)。

## 一、为什么要自动化与工程化？

问题不是手工一定不可复现：人写的提示也可进入 Git、评测与发布链。自动化主要针对这些瓶颈：

1. **搜索成本高**：大量候选、模块组合和边界样本难以靠人工逐一比较；
2. **实验记录不足**：「上次那版更好」却找不回配置、样本和逐题结果；
3. **脆弱**：改一句 system prompt 可能让 A 场景变好、B 场景变差而无人察觉。

解法分两层：自动优化生成/筛选候选；运维冻结结果、验收与发布。无需自动搜索也能先做好运维，自动优化器也无权直接发布生产模板。若缺少正确政策资料、检索权限或工具能力，搜索话术不是根因修复。

## 二、自动提示优化方法

### APE（Automatic Prompt Engineer）

[APE 原论文](https://arxiv.org/abs/2211.01910) 把指令看作待搜索程序：提案模型根据输入/输出示例生成候选，任务模型执行候选，评分后选出表现较好的指令。所测任务中的优于/接近人工指令，不等于所有任务都能自动找到最优。

这里至少有三种身份：**提案模型、任务模型、评分器**，它们可以复用同一服务，但职责与调用必须分开记录。提案用 train 示例，筛选用 development 样本，最终验收用未参与搜索的 holdout；被反复用来选候选的“校验集”不是独立测试集。只靠 JSON 合法率筛选，会选出格式好但内容错的提示。

### OPRO（Optimization by PROmpting）

[OPRO](https://arxiv.org/abs/2309.03409) 把历史候选及分数作为上下文，生成新候选，再由外部过程评分并加入历史。不同于纯随机生成，它利用搜索历史；但 LLM 不因此成为有单调改进或全局收敛保证的数值优化器。

若评分噪声大，优化器可能追逐一次偶然高分；历史过长也会挤占上下文。保留历次最优候选、逐题结果和试次，而不是无条件用“最后生成”的版本。题目不变的情况下，“深呼吸”一类措辞可作为待测试候选，不应解释成生理机制，也不保证跨模型/语言迁移。

### DSPy（声明式提示编程框架）✅ 工程主流

本节保留旧标题以兼容锚点；“工程主流”不作为使用率排名。DSPy 把程序拆成声明式 LM 模块：Signature 定义输入、输出与任务约定，模块组织预测/推理/工具流程，优化器按指标调整支持的参数。它减少手工耦合，不取消任务定义、数据清理与指标设计。

```
你写：签名（输入字段 → 输出字段）+ 模块（Predict/ChainOfThought/ReAct）
DSPy：选择具体优化器，在 train/development 上搜索它支持的参数
     保存候选程序，再到独立 holdout 验收；不是自动发布
```

- [DSPy 论文](https://arxiv.org/abs/2310.03714) 用“编译”组织程序优化；不是证明功能等价的传统编译器，也不保证搜索最优。不同优化器可调整示例、指令或其他支持的参数，不能一概说只改字符串或必然训练权重。
- [BootstrapFewShot 官方源码](https://github.com/stanfordnlp/dspy/blob/main/dspy/teleprompt/bootstrap.py) 收集 teacher 轨迹和带标签示例；有 metric 时按它决定是否接受。没有 metric 时，该读取实现不检查业务正确性，因此“框架生成的示例”并不自动可信。
- [MIPROv2 官方源码](https://github.com/stanfordnlp/dspy/blob/main/dspy/teleprompt/mipro_optimizer_v2.py) 分为示例候选、指令候选和参数搜索，`prompt_model` 与 `task_model` 可不同。要分别记录提案、任务、bootstrap 和评估费用，而不是只看一次 compile 的名字。
- 换模型可重新搜索降低部分人工工作，但仍要检查模型接口、工具/输出兼容、指标与数据分布；旧示例可能不适用，重新编译不是免回归通行证。

**一个已核源码的门槛陷阱。** 本轮读取的 BootstrapFewShot `main` 实现，在阈值不是 `None` 时比较 `metric_val >= metric_threshold`。Python 中 `False >= 0` 为真，所以布尔 metric 配 `metric_threshold=0` 会接受错误样本；布尔 metric 应使用布尔验收语义，数值 metric 才配合理阈值。没有 metric 也不能靠默认接受声称数据正确。实际安装版需按 commit/版本复核，不能把本文所读 main 当所有版本行为。

### TextGrad（文本梯度）

[TextGrad](https://arxiv.org/abs/2406.07496) 把 LLM 的自然语言反馈沿计算图传回可优化变量，可用于提示、代码等组件。这里的“梯度”是文本反馈类比，不是对离散字符串求得的解析导数，也不保证沿反馈更新一定降低真实损失。

它的价值是把“最终输出哪里不好”关联到可修改组件；失败模式是反馈归因错、局部修好全局变坏、裁判与任务模型共享偏差。优化器只改候选变量，冻结不可变业务规则与权限；每轮保留旧候选，用独立验收决定是否接受，不让评测样本的恶意文本改写上层指标。

### 方法对比

| 方法 | 主要搜索对象/组织方式 | 信号 | 典型失效 |
| --- | --- | --- | --- |
| APE | 生成候选指令后筛选 | 示例与执行评分 | 筛选集过拟合、候选缺有效多样性 |
| OPRO | 用历史候选/得分提出新指令 | 历史评估值 | 追逐噪声、上下文中遗失关键约束 |
| DSPy | 模块程序及所选优化器支持的参数 | teacher 轨迹、标签、metric | 错误示例被接受、端到端指标隐藏节点失败 |
| TextGrad | 计算图中可修改变量 | 沿依赖传播的文本反馈 | 反馈归因错误、语言改进不等于真实损失下降 |

共同前提是可获得的反馈与明确目标，但信号可以是标签、规则、执行结果或自然语言评价，不必全是同一种标量分数。**优化目标必须接受元评估**：先检查评分器与人工/业务标签是否一致，再让优化器放大它。

### 先防“优化了错误指标”

构造 100 条订单抽取题，90 条应有唯一订单号、10 条确实未知。一个永远输出合法 JSON 且 `order_id=null` 的候选，格式率可为 100%，但订单字段正确率只有 10%。若指标只奖励格式或“谨慎拒答”，搜索会把它当好方案。

更稳妥的验收分层：先检查输出 schema 与受保护规则；再按字段标签、证据支持、歧义追问的 precision/recall 评分；最后看成本、延迟与业务切片。涉及工具动作时，授权仍由执行器强制；即使测试中零次越权，也不是无权限风险的证明。不要用一个加权平均，让质量小幅上涨抵消一次真实越权。

模型裁判需固定版本、量表、提示与输入展示方式，并抽样对照人工/规则。优化器可能生成迎合裁判的冗长答案或夹带评分指令；评分输入当不可信数据处理，最终 holdout 和关键红线不由候选自己定义。

### 一次可核查的优化实验

```text
固定任务、允许修改变量、模型、工具快照与预算
  -> 划分 train / development / holdout（按用户或文档去近重复）
  -> 记录手写基线与各切片失败
  -> 用 train 提案/收集示例，development 比较候选
  -> 冻结候选与优化记录
  -> 独立 holdout + regression 验收，保留逐题退化
  -> 审阅后交给发布链，不由优化器直接上线
```

如果每一轮都查看 holdout 再改提示，它已变成开发集；换个文件名不能修复泄漏。自动生成示例也可能带错标签、隐私或注入，需过滤、授权和来源记录。固定随机种子仅记录部分随机性，远端服务与 teacher 的输出仍可能变化。

**预算构造。** 20 个候选、100 条 development 样本、每条重复2次，若每个样本有2个 LM 模块再加1次模型裁判，则完整评估需要 $20\times100\times2\times(2+1)=12,000$ 次调用；另有提案、bootstrap、基线和 holdout 费用。若用规则评分，最后的裁判调用可移除，但工具/检索调用仍另计。早停和 minibatch 可省钱，也会使筛选更受噪声影响；需在选中后做完整验收，不能把小批最高分当最终效果。

[OPRO 官方仓库](https://github.com/google-deepmind/opro) 明确提醒优化/评估调用可能产生较大费用。本文不提供当前报价；记录每类模型的输入/输出 token、缓存与重试，再按真实单价计算。

## 三、提示工程化运维（Prompt Ops）

把提示当代码管理，最小可用体系：

| 维度 | 做法 |
| --- | --- |
| **版本化** | 保存模板、编译程序、示例库、模型/优化器、指标和实验配置，指向不可变 revision |
| **评估集** | 样本量按风险/切片与不确定性决定；小集合可找错误，不自动证明可上线 |
| **回归测试** | 每次改提示在评估集上对比，CI 里挡住「改好 A 改坏 B」的隐性回归 |
| **环境隔离** | dev/staging/prod 提示独立发布，与代码同等发布纪律 |
| **A/B 与灰度** | 高风险改动先小流量灰度，看质量 + 业务指标再放量 |
| **监控** | 业务反馈与规则/人工核对优先，模型 judge 经校准作辅助，关联实际版本与切片 |

评估方法（judge 偏差、meta-evaluation 等）见 [模型评估](/evaluation/evaluation)；完整生产运营见 [LLMOps](/engineering/llmops)。

## 四、上游模型变更：被忽视的风险

API 模型升级、微调版本切换、甚至供应商静默更新，都可能改变模型行为，让原本调好的提示失效。纪律：

- 模型可锁快照时锁定并记录；不能锁时说明限制，记录实际路由和漂移证据；
- 切换模型前**全量跑评估集**对比，灰度放量；
- 重新搜索前检查输出/工具能力与数据分布，编译后的程序和示例重新验收；框架不能弥补目标模型缺失的能力。

## 五、什么时候该上自动优化？

- **别过早优化**：任务简单、几条清晰指令就够时，手写 + 小评估集足矣；
- **该上的信号**：任务多、提示复杂、要频繁换模型、对指标有硬要求、人工调试已成瓶颈；
- **永远先有评估集**：无论手工还是自动，没有可打分的评估集，一切「优化」都是凭感觉。

按失败原因判断是否值得投入：指令含糊先人工澄清；示例选择成为瓶颈可测试 bootstrap；多模块相互影响可测试程序优化；缺事实或坏工具先修资料/执行器。上线后才能观察到的业务指标，应先建立可用的离线代理并检验相关性，不能直接把用户流量当无限优化实验。

<details>
<summary>L1：订单抽取为什么不该只用 JSON 合法率优化？</summary>

合法 JSON 不代表订单号正确。常量 null 在构造集合中格式100%、订单字段仅10%；先定义标签、未知与歧义规则，再比较手写基线和候选。能解释输入、metric与失败例，比背优化器名称更重要。
</details>

<details>
<summary>L2：一次 compile 涨分，如何判断是否值得发布？</summary>

检查独立 holdout、关键切片、错误示例、评分器偏差及12,000次构造调用账本；保存候选与版本，让发布链验收和灰度。模型替换仍需兼容/回归，不把编译成功当线上质量保证。
</details>

<details>
<summary>L3：自动方案胜过手写，如何排除搜索预算造成的假象？</summary>

建立同模型、同数据、同调用/token预算的人工/随机搜索/自动优化对照；分别消融示例、指令、teacher与评分器。重复搜索报告分布、失败与逐题退化，最终选择不看holdout；不同预算曲线比单个最好分数更能支持结论。
</details>

**来源阅读边界：** 实读 APE、OPRO、DSPy、TextGrad 论文题名/摘要，未逐页核实验或复现。实读 DSPy 官方 main 中 BootstrapFewShot 的初始化/metric验收/轨迹收集，以及 MIPROv2 的模块候选和搜索阶段；未审全仓库或安装版。实读 OPRO README 的用法、历史依赖与费用提醒，不把其旧SDK示例当当前API教程。图示、常量null和调用数为构造，未安装DSPy/TextGrad、编译程序或调用模型。

## 高频追问

**Q：DSPy 解决了手工提示工程的什么问题？**
它解耦任务签名、模块流程和可搜索参数，便于用指标比较候选；不是取消手工设计或保证最优。不同优化器搜索对象不同，换模型需重新检查兼容和验收。

**Q：OPRO 为什么能搜出「深呼吸再做题」这种怪提示？**
它利用历史候选与分数生成新候选，自然语言空间可包含反直觉措辞。但某句话在一个实验有效不代表全球最优或真实“深呼吸”机制；需与随机搜索、同预算基线及独立验收比较。

**Q：自动提示优化的共同前提是什么？**
明确目标、可获得反馈与独立验收。反馈可以是规则、执行结果或文本，不必同一种标量；先元评估评分器，避免自动化更快地优化错目标。

**Q：怎么安全地把一次提示改动上线？**
冻结候选和依赖，在独立验收/回归上过质量、安全与预算门禁，再进入隔离副作用的 shadow 和受控灰度。回退切换兼容 manifest，不撤销已发生业务动作；详见 [生命周期](/prompt/prompt-lifecycle)。

**Q：模型升级会让提示失效吗？怎么应对？**
可能退化，也可能改善。记录实际模型/路由，比较完整验收与关键切片，检查示例及工具兼容；重新搜索只是候选生产，不能替代门禁。不能锁快照时明确重放限制并监控漂移。

**Q：TextGrad 和 DSPy 都是自动优化，区别是什么？**
DSPy 组织声明式模块程序，由具体优化器选择参数；TextGrad 沿图传播文本反馈到可修改变量。编译与梯度是组织/优化类比，不是等价转换或解析导数保证；两者都需独立验收。
