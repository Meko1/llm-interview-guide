# Agentic RAG（智能体检索增强）

> 本文把「朴素 RAG」限定为单次检索后生成的基线，而不是所有非 Agent 的 RAG。固定工作流也能做查询分解、重排和多轮检索；Agentic RAG 的区别是模型参与选择下一步动作。基础概念见 [RAG 基础](/rag/rag-basics)、Agent 概念见 [Agent 基础](/agent/agent-basics)。

## 一、为什么需要 Agentic RAG？

朴素 RAG（Naive RAG）的结构性缺陷：

| 缺陷 | 表现 |
| --- | --- |
| 单次检索 | 证据不全时可能答错，也可能正确拒答 |
| 多跳受限 | 后续查询依赖前一步实体时，单次召回未必覆盖全部证据 |
| 不判断相关性 | 检索到的垃圾也照单全收，污染生成 |
| 不会反思 | 答错了不会重试、不会换个查询 |
| 总是检索 | 「你好」这种问题也去查库，浪费且引噪声 |

Agentic RAG 用一个（或多个）LLM Agent 来**编排**检索过程，把上面每个缺陷都变成「可决策的一步」。

## 二、核心能力拼图

Agentic RAG = RAG + Agent 的四种能力：

```
        ┌─────────────── Agent 决策循环 ───────────────┐
用户问题 → 是否需要检索? → 生成/改写查询 → 检索 → 评估检索质量 → 够了? → 生成答案
              │否              ↑                              │不够        │
              直接答 ←─────────┴──────── 改写查询/换工具/多跳 ←┘           反思校验
```

1. **路由（Routing）**：判断该不该检索、该查哪个数据源（知识库/网络/数据库/工具）。
2. **查询规划（Planning）**：把复杂问题分解成子查询，或规划多跳检索路径。
3. **反思（Reflection）**：评估检索结果相关不相关、答案有没有依据，不行就重来。
4. **工具调用（Tool use）**：检索只是工具之一，还能调用计算器、SQL、API、网页搜索。

## 三、代表方法

### Self-RAG（自反思 RAG）

训练模型在生成时输出特殊的「反思 token」，自主决策：

- **Retrieve token**：这一步要不要检索？
- **IsRel**：检索到的内容相关吗？
- **IsSup**：我的生成被检索内容支持吗（有没有幻觉）？
- **IsUse**：这个回答有用吗？

模型边生成边自评，按需检索、自我批判，把「检索 + 质量控制」内化进生成过程。

### CRAG（Corrective RAG，纠错 RAG）

给检索结果加一个**轻量评估器**打分，按结果分三档处理：

- **Correct**（检索可靠）：精炼后使用；
- **Incorrect**（检索不可靠）：丢弃，转**网络搜索**兜底；
- **Ambiguous**（不确定）：两者结合。

核心思想：**用质量门控选择后续路径**。评估器也会误判，网络搜索也可能返回错误或无权使用的资料；论文任务上的改进不能直接当作企业知识库的准确率承诺。

### 多跳 / 迭代检索（Iterative Retrieval）

复杂问题分轮检索，每轮用上一轮的结果决定下一步查什么：

```
Q：「写《三体》的作者获得的雨果奖是哪一年颁发的？」
跳1：检索「《三体》作者」→ 刘慈欣
跳2：用「刘慈欣 雨果奖 年份」再检索 → 2015
```

代表思路如 IRCoT（检索与思维链交替）、ReAct 式「想—查—想—查」循环。

### Agentic / 多 Agent RAG

把检索能力封装成工具，由 ReAct Agent 自主调度；复杂场景用多 Agent 分工（一个 Agent 管知识库、一个管网络、一个汇总），见 [多 Agent](/agent/multi-agent)。这是与通用 Agent 框架（LangGraph 等）结合最紧的形态。

## 四、Naive RAG vs Agentic RAG

| 维度 | Naive RAG | Agentic RAG |
| --- | --- | --- |
| 检索次数 | 固定一次 | 按需多次/不检索 |
| 多跳问题 | 可能一次召回覆盖，但缺少自适应下一跳 | 可显式迭代，不保证找到证据 |
| 相关性判断 | 基线未配置，可增加固定门控 | 可参与反馈决策，仍需校准 |
| 兜底 | 可以配置确定性拒答或换源 | 换源/重试/拒答需受政策约束 |
| 延迟 | 路径较固定 | 分布更宽，需轮数与截止时间上限 |
| 成本 | 低 | 高（多次 LLM + 检索调用） |
| 适用 | 简单事实问答 | 复杂、多跳、高准确率要求 |

> 务实原则同 [工作流 vs Agent](/agent/workflow)：**简单问答别上 Agentic RAG**，它的自主性带来延迟和成本，只在朴素 RAG 确实答不好时才引入。

## 五、工程落地要点

- **延迟与成本控制**：多轮检索 + 反思会让一次问答跑好几次 LLM，必须设最大轮数、加缓存、对简单问题走快速路径（路由分流）。
- **可观测性**：Agentic 流程是黑盒，必须 trace 每一步「查了什么、评估结果、为什么重试」，否则无法调试（见 [LLMOps](/engineering/llmops)）。
- **评估**：除了答案质量，还要评估「检索决策对不对、多跳路径合不合理」，见 [RAG 评估](/rag/rag-evaluation)。
- **防失控**：反思循环可能停不下来或越查越偏，要有收敛条件和兜底答案。

## 高频追问

### 落地练习：证据不足时下一步由谁决定？

假设是只读的企业政策问答，允许最多两轮检索，不允许访问公网。状态至少记录 `query`、已查来源、证据 ID、轮数、剩余时间和终止原因。模型可以建议改写查询，但执行器只允许访问当前用户有权读取的索引；「搜索公网」即使被模型提出也必须拒绝。

| 观察 | 下一步 | 验证证据 |
| --- | --- | --- |
| 第一跳有实体，第二跳缺政策条款 | 用实体与政策版本定向检索 | 每跳的可见候选与最终引用分开记录 |
| 相同查询反复返回相同片段 | 停止并报告不足 | 不把多次调用当作新增证据 |
| 有相关条款，但不同版本冲突 | 保留版本差异并请求澄清 | 引用原文、版本与位置，不只引用摘要 |
| 时间或轮数耗尽 | 返回有依据的部分结论或拒答 | 明确缺失的证据，不输出「已全面核实」 |

检索层测每跳 Recall@k 和权限过滤后的覆盖率；回答层测声明是否受来源支持、引用是否正确及应拒答时是否拒答；编排层另测路由、循环率、预算违约和多次独立试验的成功率。不要用最终答案分数代替所有中间层指标。

**Q：Agentic RAG 和普通 RAG 的本质区别？**
普通 RAG 是固定的「检索→生成」管道；Agentic RAG 让 LLM 自主决策检索流程——要不要检索、查什么、查几次、结果可不可信、要不要换源重试。本质是把「静态流水线」变成「带反馈的决策循环」。

**Q：Self-RAG 和 CRAG 有什么区别？**
Self-RAG 是**训练**模型输出反思 token、把按需检索和自我批判内化进生成；CRAG 是在检索后挂一个**外部评估器**给结果打分、不行就转网络搜索兜底，不需要改模型。前者改模型、后者改流程，可结合。

**Q：多跳检索为什么朴素 RAG 做不了？**
单次检索可能同时找到两跳证据，但当第二跳实体必须从第一跳确定时容易漏证据。可以用固定的查询分解工作流，也可以让 Agent 选择下一跳；需要迭代不等于必须采用自主 Agent。

**Q：什么时候不该用 Agentic RAG？**
简单事实问答、延迟敏感、成本敏感的场景。它的多轮 LLM 调用会让延迟和成本翻几倍，对「一次检索就能答好」的问题是浪费。用路由先分流，复杂的才进 Agentic 流程。

**Q：Agentic RAG 的主要工程风险？**
延迟/成本不可控（多轮循环）、反思可能不收敛或越走越偏、黑盒难调试。对策：最大轮数限制、快速路径分流、全链路 trace、兜底答案、对检索决策单独评估。

**Q：Agentic RAG 和长上下文模型是替代关系吗？**
不完全是。长上下文能「把更多内容塞进去」，但仍受成本、lost-in-the-middle 和知识时效限制；Agentic RAG 强在「按需精准取用 + 多跳推理 + 外部工具」。趋势是结合：长上下文承载单轮更多材料，Agentic 编排多轮与多源（见 [长上下文专题](/basics/long-context)）。
