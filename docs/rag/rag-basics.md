> **先回答一个问题：正确证据，是否在正确权限与版本下进入了回答？** RAG 的价值是建立可检查的证据通道，不是给模型接上向量库就保证正确。

## 一、什么是 RAG？为什么需要它？ {#rag-definition}

<span id="一、什么是-rag-为什么需要它"></span><span id="十三、面试加厚版-rag-的核心心智模型"></span>

RAG（Retrieval-Augmented Generation，检索增强生成）让系统先获取外部材料，再把材料作为生成回答的依据。适合需要引用、更新或访问私有知识的任务，但检索和生成都可能出错。

可以把一次回答理解为五个问题：资料有没有接入？证据有没有找全？上下文有没有正确组织？结论有没有证据支持？用户是否有权使用这些资料？

**原始论文与工程用法要分开。** Lewis 等人的 RAG 模型把检索文档作为潜变量，联合建模检索与生成。许多业务系统冻结模型，把检索结果拼入 Prompt；它们也被称为 RAG，但不等于复现了原论文的训练方式。

## 二、RAG vs 微调 vs 长上下文 {#rag-choices}

<span id="选型依据与反例"></span><span id="二、rag-vs-微调-vs-长上下文"></span><span id="七、rag-范式演进"></span><span id="二十六、不同业务场景的-rag-设计差异"></span><span id="_26-1-企业知识库问答"></span><span id="_26-2-客服-rag"></span><span id="_26-3-法务-合同-rag"></span><span id="_26-4-金融投研-rag"></span><span id="_26-5-代码知识库-rag"></span><span id="二十七、rag-与-agent-的关系"></span>

| 任务约束 | 可以先试什么 | 必须验证的反例 |
| --- | --- | --- |
| 小而固定的一组材料 | 直接放入长上下文 | 证据位置、token 成本、引用与权限 |
| 文档频繁更新、需要溯源 | RAG | 索引延迟、漏召回、过期与冲突材料 |
| 固定输出格式或任务行为 | Prompt 基线，再评估 SFT / LoRA | 数据是否改善 held-out 任务，是否遗忘 |
| 产品编号、合同条款精确定位 | 关键词检索或混合检索 | 分词、编号规范化、误匹配 |
| 关系查询、跨文档综合 | 分解检索；必要时评估图或迭代检索 | 新增构建成本、错误传播、权限继承 |

这些方法可以组合。不要把“新知识只能 RAG”“微调一定更好”“复杂问题一定 GraphRAG”当作定律。先用同一问题集对比简单基线，新增组件需要可测量收益。

RAG 作为 Agent 的工具时，返回证据、来源和限制，而不是替 Agent 授权执行。让模型动态检索也会增加循环成本；固定一次检索能完成任务，就不必增加规划器。

## 三、完整架构总览 {#rag-architecture}

<span id="三、完整架构总览"></span>

```text
离线：源文档 → 解析检查 → 版本与权限元数据 → 切分 → 索引快照
在线：用户身份 → 检索范围 → 候选召回 → 重排 → 上下文 → 生成 → 引用校验
观测：问题、快照、候选、过滤、重排、上下文、回答、成本与失败类别
```

离线与在线链路共享文档身份、权限策略和版本。只记录最终答案，无法判断问题出在解析、召回还是生成。trace 也不是无限制的原文日志：敏感资料要脱敏、控制访问和保留期。

## 四、离线索引详解 {#rag-data}

<span id="四、离线索引详解"></span><span id="_4-1-加载与解析-load-parse"></span><span id="_4-2-切分-chunking-——最关键、最易被深问"></span><span id="_4-3-向量化与入库"></span><span id="十四、rag-的数据工程-比向量库更早决定上限"></span><span id="_14-1-文档接入要问清楚什么"></span><span id="_14-2-解析质量决定召回上限"></span><span id="_14-3-元数据不是附属品"></span><span id="十五、chunking-的深挖追问"></span><span id="_15-1-chunk-大小怎么定"></span><span id="_15-2-overlap-不是越大越好"></span><span id="_15-3-父子分块怎么讲"></span>

**先检查解析，再调模型。** PDF 多栏顺序错乱、表格表头丢失、OCR 编号识别错误，会直接污染证据。抽样对照原页与解析文本，记录 parser 版本、页码、标题路径和表格结构。

| 字段 | 为什么需要 |
| --- | --- |
| document_id / chunk_id | 追踪原文、删除与稳定引用 |
| document_version / content_hash | 识别更新、复现知识快照 |
| source / page / title_path | 人工核查与定位上下文 |
| valid_from / valid_to | 区分发布时间与实际生效时间 |
| tenant_id / ACL 引用 | 限定检索范围，而非交给模型判断 |
| parser_version / embedding_version | 解释重建与结果变化 |

**切分单位不是越小越好。** 小块定位更细，但可能切断条件；大块保留上下文，却可能混入多个主题。按文档结构切分，并在自己的 tokenizer 下统计长度。overlap 是边界补偿，也会增加索引与上下文重复；不宜把某个比例当成通用最优值。

父子分块可以用小块检索、回填父段解释，但父段同样要做权限和预算检查。表格片段应保留表头、单位和行列关系，不把“300”单独当作完整证据。

**增量更新不是只做 upsert。** 新版本切分后，旧版多余 chunk 需要撤销；删除、撤权、embedding 变更也要进入更新流水线。多存储系统不能假设原子切换，可用快照版本和发布指针避免在线混用半套索引。撤权要有快速阻断路径，不能只等待下一次全量重建。

## 五、在线检索与生成详解 {#rag-retrieval}

<span id="五、在线检索与生成详解"></span><span id="_5-1-查询处理-pre-retrieval"></span><span id="_5-2-检索-retrieve"></span><span id="_5-3-重排-rerank-可选但高性价比"></span><span id="_5-4-上下文组装-augment"></span><span id="_5-5-生成-generate"></span><span id="六、向量检索原理"></span><span id="十六、embedding-与检索的面试追问"></span><span id="_16-1-为什么纯向量检索不够"></span><span id="_16-2-混合检索怎么融合"></span><span id="_16-3-query-rewrite-什么时候有用"></span><span id="十七、rerank-的深挖"></span><span id="_17-1-为什么-reranker-更准"></span><span id="_17-2-rerank-排错怎么做"></span>

1. 从可信身份上下文确定租户、角色和文档范围，不接受模型自报 tenant_id。
2. 规范化 query；若改写，保存原始问题与改写结果，防止产品型号、否定条件或时间被改掉。
3. 召回候选：关键词与向量可以互补。向量 query 编码器和文档编码器必须属于兼容的检索空间，不要求它们一定是同一组权重；双编码器可以分别训练。
4. 重排候选：reranker 能改变排序，不能找回未召回的证据。记录召回数、重排数和最终保留数，别把三个 K 混为一谈。
5. 过滤和组织证据，再生成与校验回答。

向量相似度不是答案正确概率，不同模型的分数阈值也不能直接移植。BM25 与向量分数尺度不同；融合时可评估基于排名的 RRF，但其参数和效果仍需在任务上验证。

**调参应由失败类型驱动：** 编号遗漏先看关键词通道；候选有证据但排名低再看重排；候选已正确却被截断，修上下文；没有材料可回答时，换更强模型也不能制造可信证据。

## 六、上下文组织与引用 {#rag-context}

<span id="十八、上下文组织-rag-不是把-top-k-直接拼进去"></span><span id="_18-1-上下文组织要做哪些事"></span><span id="_18-2-lost-in-the-middle-怎么缓解"></span><span id="_18-3-文档冲突怎么处理"></span>

最终上下文至少保留来源 ID、版本、生效条件和足够的原文。去重时不要删掉独立佐证；压缩时不要丢掉否定、例外、单位与条件。摘要也是模型生成的产物，可能失真，需要对照原证据检查。

上下文预算应覆盖系统指令、历史、问题、工具说明、证据和预留输出。只按文档长度占满输入窗口，可能使回答被截断。Lost in the Middle 给出了特定模型和任务下的位置效应实验，不代表每个新模型都以相同比例失效。

引用校验分两层：

- **存在性**：引用 ID 是否真实来自本次允许使用的上下文？
- **支持性**：该片段是否支持这条主张，且对象、时间和条件一致？

“引用能打开”不等于“引用支持结论”。资料不足、冲突无法消解时，应说明缺少什么、澄清或转人工；降低温度和加强 Prompt 都不能保证消除幻觉。

## 七、权限、多租户与安全 {#rag-security}

<span id="十九、权限、多租户与安全"></span><span id="_19-1-权限必须在检索前过滤"></span><span id="_19-2-多租户-rag-怎么设计"></span><span id="_19-3-间接-prompt-injection"></span>

权限要覆盖索引、检索、父段回填、缓存、上下文、引用链接和日志。不能先把越权内容发给模型，再指望答案过滤补救。支持预过滤的索引优先限定搜索范围；只能后过滤时，还要评估候选不足、信息泄露与召回代价。

缓存命中也要核查身份、授权版本和知识快照。语义相似问题不一定属于同一租户、日期或业务对象；仅以 query 为键共享答案是风险。用户点击引用时，原文服务也要重新鉴权。

检索到的网页与文档是**不可信数据**。其中的“忽略规则”“外发材料”不是系统指令。提示隔离是辅助措施，真正的权限和工具策略必须由模型外部执行。参见 [工具安全](/agent/tool-safety) 与 [多租户 RAG 治理](/interview/multi-tenant-rag-index-governance-playbook)。

## 八、RAG 评估：先定义分母 {#rag-baseline}

<span id="先建立可测量的基线"></span><span id="八、rag-评估"></span><span id="二十、rag-评测体系怎么搭"></span><span id="_20-1-先拆检索和生成"></span><span id="_20-2-golden-set-怎么建"></span><span id="_20-3-资料不足时怎么评"></span><span id="二十九、rag-和评测集的数据飞轮"></span>

固定问题集、知识快照、模型、Prompt 和权限条件，分层记录：

| 层次 | 检验问题 | 指标与限制 |
| --- | --- | --- |
| 召回 | 必需证据是否进入候选？ | Recall@K；需要证据标注，不是只看语义相关 |
| 排序 | 正确证据排在哪里？ | MRR 看首个相关结果；多证据题还需覆盖指标 |
| 上下文 | 证据是否完整保留？ | 证据覆盖、冲突、权限、截断与预算 |
| 生成 | 主张是否被支持？ | 人工核查、引用支持率、忠实度；Judge 需校准 |
| 业务 | 是否帮助正确行动？ | 任务完成、误导、拒答与转人工，不只满意度 |

**Recall 与 Hit Rate 不能混用。** 单个问题需要两段证据，找回一段时 Recall 是 1/2，而“至少命中一段”的 Hit 为 1。下面是构造样例，只有集合复算，不调用检索器或模型。

```python
gold_sets = [{"a", "b"}, {"c"}, {"d"}]
retrieved_sets = [{"a", "x"}, {"c", "y"}, {"z"}]
recalls = [len(gold & found) / len(gold)
           for gold, found in zip(gold_sets, retrieved_sets)]
hits = [bool(gold & found)
        for gold, found in zip(gold_sets, retrieved_sets)]
print(f"Macro Recall: {sum(recalls) / len(recalls):.3f}")
print(f"Hit Rate: {sum(hits) / len(hits):.3f}")
```

预期输出：

```text
Macro Recall: 0.500
Hit Rate: 0.667
```

无答案问题没有这个证据分母，应单独统计正确拒答与错误作答。问题集至少覆盖可回答、资料不足、歧义、时效冲突、跨段、多租户越权和表格编号。

划分训练与评测时按来源或时间去重，避免同一文档改写泄漏。新增组件只改一个变量：先比无检索与简单检索，再比混合召回或重排；记录分场景质量、p95 延迟、token 与成本。线上 bad case 可回流到开发集，但固定验收集不应反复用于调参。

<details>
<summary>L3 / L4 追问：怎样解释实验收益？</summary>

若重排提升了整体答案分数，要检查是否同时改变了候选数、上下文长度、模型或评审 Prompt。报告标注方法、样本数、各类别结果及不确定性。检索论文上的平均收益不能直接外推到企业权限、更新与长表格场景。

</details>

## 九、常见失败模式与排查 {#rag-failures}

<span id="失败案例-资料找到了-答案为什么还错"></span><span id="九、常见失败模式与排查"></span><span id="十、面试专项-rag-排障四步法"></span><span id="二十三、rag-高频事故复盘"></span><span id="事故一-回答引用了用户无权限文档"></span><span id="事故二-文档更新后仍回答旧政策"></span><span id="事故三-召回很多但答案很差"></span><span id="事故四-用户问编号查不到"></span>

| 可观察现象 | 先核查什么 | 不宜直接做什么 |
| --- | --- | --- |
| 原文有答案，候选没有 | 解析、切分、过滤、query 改写、召回通道 | 直接换生成模型 |
| 候选有答案，最终上下文没有 | 重排、去重、父段回填、截断 | 盲目增加 top-k |
| 上下文正确，回答仍错误 | 条件、单位、冲突、生成与引用支持 | 把相关度当忠实度 |
| 新文档已上传，仍答旧政策 | 生效日期、索引快照、缓存与引用版本 | 只重新上传一次 |
| 单一租户正常，跨租户泄漏 | 检索范围、回填、缓存键、原文鉴权 | 只在 Prompt 中写禁止泄漏 |

**构造案例：报销标准从 500 元改为 300 元。** 先核实问题中的报销日期和适用对象，不是机械选择更新时间最新的文档。记录旧新政策、有效期、检索快照与缓存版本；只有确认新版适用，才能采用 300 元。无法确认时澄清，不能拼成平均值或让模型自行“折中”。

四步诊断：原文是否正确 → 候选是否覆盖 → 上下文是否完整且适用 → 主张是否被支持。修复后把这个案例加入回归集，并检查旧版适用的历史报销是否仍能回答。

## 十、容量估算：先数 token 与 chunk {#rag-capacity}

<span id="三十五、rag-现场白板题-给你-10-万份文档怎么做"></span>

下面是教学假设，不是生产测量：100,000 份文档，每份在所选 tokenizer 下恰好 2,000 token；固定窗口 500 token、overlap 50 token，末尾保留不足窗口的片段。

每份文档的窗口数为 1 + ceil((2000 − 500) / (500 − 50)) = 5，总计 500,000 个向量。若每个向量 768 维、float32，纯向量数据约 500000 × 768 × 4 = **1,536,000,000 字节，约 1.43 GiB**。

这不含 ANN 索引、原文、元数据、副本、关键词索引、构建峰值和缓存，不能拿它当磁盘或内存采购值。真实分布、结构切分、重复文档和 tokenizer 会改变 chunk 数。线上容量还需按过滤、重排与生成链路压测；文档总量不能直接推导 QPS。

## 十一、生产化考量 {#rag-production}

<span id="十一、生产化考量"></span><span id="二十一、rag-系统设计题答法"></span><span id="二十八、rag-的上线监控指标"></span><span id="系统指标"></span><span id="检索指标"></span><span id="生成指标"></span><span id="业务指标"></span><span id="三十一、rag-终极系统设计模板"></span>

上线前写清“不允许出什么错”，再确定门禁：越权泄漏、错误引用和错误业务指引通常不能被平均分掩盖。阈值来自业务风险与基线，不在本页编造统一百分比。

- **发布**：解析、切分、embedding、索引、reranker、Prompt 与模型一起记录版本；影子流量须遵守同样权限。
- **更新**：监控接入到可检索的延迟、删除和撤权传播；失败索引不能替换健康快照。
- **降级**：重排不可用时可退回允许的检索基线；资料或权限不确定时说明限制，不生成貌似完整的答案。
- **监控**：分别观察分段错误、p50/p95 延迟、成本、缓存错误和拒答；转人工下降也可能是错误自信增加。
- **回滚**：恢复模型与索引版本，并验证缓存、引用和授权仍一致，不只换回 Prompt。

白板题“给你 10 万份文档”应先问文档类型、权限、更新、查询负载和引用要求，再展开上述链路。完整练习见 [RAG 系统设计](/interview/application-system-design)。

## 十二、分层面试追问与自测 {#rag-interview}

| 层级 | 追问 | 回答应展示的证据 |
| --- | --- | --- |
| L0 / L1 | 为什么已经召回，模型还会答错？ | 一条完整候选、上下文、主张对照 |
| L1 | query 与文档必须用同一模型吗？ | 兼容编码空间与双编码器的区别 |
| L2 | 父段回填、缓存和引用怎么鉴权？ | 身份来源、授权版本与拒绝路径 |

项目表达只保留一套结构：**任务约束 → 简单基线 → 一个失败 → 定位证据 → 改动 → 回归与代价**。如果只跑过 Demo，就明确数据规模、未实现的权限与未验证的负载，不伪装成生产系统。

自测：能否复算 Recall？能否说明一个“不该增加 top-k”的反例？能否区分引用存在与支持？能否解释撤权如何作用于缓存？能否对一个失败给出可验证的修复？

## 一手参考与适用边界 {#rag-sources}

<span id="一手参考"></span>

- [Lewis 等：Retrieval-Augmented Generation（2020）](https://arxiv.org/abs/2005.11401)：原始检索与生成建模，不等同于所有业务拼接实现。
- [Liu 等：Lost in the Middle（2023）](https://arxiv.org/abs/2307.03172)：特定模型与任务下的上下文位置实验，不是通用退化比例。
- [Thakur 等：BEIR（2021）](https://arxiv.org/abs/2104.08663)：异构检索评测，提醒我们按任务检验泛化。

本页复算使用构造数据；架构建议是需要按业务验证的工程判断，不构成端到端效果保证。
