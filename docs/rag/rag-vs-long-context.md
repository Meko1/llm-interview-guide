# RAG vs 长上下文 vs 微调：选型决策

> 「想让模型用上我的知识，到底该用 RAG、把资料全塞进长上下文，还是微调？」这是大模型落地与面试的高频选型题。三者不是互斥的「三选一」，而是解决不同问题、可叠加组合的手段。本文讲清各自原理边界、核心对比与决策路径。RAG 见 [RAG 基础与流程](/rag/rag-basics)，长上下文见 [长上下文专题](/basics/long-context)，微调见 [微调范式（SFT / PEFT）](/finetuning/finetuning)。

## 一、先分清：它们各自解决什么

一个常见误区是把三者当成同类。其实：

- **RAG**：在推理时**外挂知识库**，解决「模型不知道某些事实/知识更新快/要可溯源」。
- **长上下文（Long Context）**：把相关资料**直接放进 prompt**，解决「单次任务需要一大段完整上下文」。
- **微调（Fine-tuning）**：改模型**权重**，解决「要稳定的风格/格式/领域语感/特定行为」，本质是**教能力，不是塞知识**。

> 一句话记忆：**RAG 管「知道什么」、微调管「怎么表现」、长上下文管「这次给它看什么」。**

## 二、RAG：原理与边界

通过检索把相关片段拼进上下文再生成（见 [RAG 基础与流程](/rag/rag-basics)）。

- ✅ **无需重训即可更新外部知识**：生效仍取决于摄取、索引发布与缓存失效延迟，不是改原文就即时生效。
- ✅ **可溯源**：答案能标注出处，企业合规友好。
- ✅ **成本可控**：只把 Top-K 相关片段进上下文，token 省。
- ✅ **可实现数据隔离**：检索前按权限/租户过滤，并隔离缓存与后续链路；不是用了 RAG 就天然安全。
- ❌ **依赖检索质量**：召回不到就答不对，对全局性问题（"总结整本书")弱。
- ❌ **链路复杂**：切分、嵌入、检索、Rerank 都要工程化（见 [RAG 生产化与系统设计](/rag/rag-production)）。

## 三、长上下文：原理与边界

怎样验证“能放进去”是否等于“能用好”，见 [长上下文验证：位置、版本冲突与无答案负例](/rag/long-context-validation)。

直接把长文档/多文档塞进模型的超长上下文窗口（几十万 token）。

- ✅ **简单**：不用建检索系统，整篇喂进去。
- ✅ **保留完整材料的机会**：有助于跨段任务，但是否更强要通过实际任务、位置与干扰对照验证，不能由窗口长度直接推断。
- ❌ **成本与延迟随长度增长**：注意力开销随序列变大，长 prompt 又贵又慢；KV Cache 显存吃紧（见 [推理优化与部署](/inference/inference-optimization)）。
- ❌ **位置利用风险**：Lost in the Middle 在论文所测模型与任务中观察到中间位置退化；应对目标模型做位置对照，不把它当所有模型的固定定律。
- ❌ **知识不持久**：每次都要重新塞，且窗口再大也有上限，海量知识库塞不下。
- ❌ **需要显式引用与隔离设计**：在入模前过滤权限、保留文档身份并验证引用；长上下文不自动做到这些，但也不是天然不能做到。

## 四、微调：原理与边界

用领域数据更新权重（全量或 LoRA/QLoRA，见 [LoRA / QLoRA 详解](/finetuning/lora)）。

- ✅ **稳定的风格/格式/行为**：固定输出格式、领域口吻、特定任务范式，效果稳定。
- ✅ **领域语感/术语**：让模型「说行话」、贴合专业表达。
- ✅ **可减少重复示例的上下文开销**：推理成本仍取决于模型、适配器是否合并及部署方式，不能保证零额外开销。
- ❌ **不擅长注入事实知识**：硬塞新事实易**灾难性遗忘**且记不牢，知识一变就得重训。
- ❌ **更新慢、成本高**：要准备数据、训练、评估、部署，迭代周期长。
- ❌ **不可溯源**：答案来自权重，说不清出处，幻觉难定位。

> 关键认知：**微调适合教「怎么做」（格式/风格/能力），不适合教「最新事实」**——后者交给 RAG。

## 五、核心对比

| 维度 | RAG | 长上下文 | 微调 |
| --- | --- | --- | --- |
| 解决什么 | 外挂可更新知识 | 单次大段上下文 | 风格/格式/能力 |
| 知识更新 | 受索引和缓存传播延迟限制 | 更新本次材料或缓存版本 | 更新权重需训练与发布 |
| 可溯源 | 需保留来源并校验支持 | 同样可标来源并校验 | 权重本身不提供可靠引用 |
| 推理成本 | 检索、重排与生成合计 | 输入、缓存与生成合计 | 取决于模型与适配器部署 |
| 前期成本 | 中（建检索链路） | 低 | 高（数据+训练） |
| 数据隔离/多租户 | 检索、回填、缓存均需 ACL | 入模前过滤与缓存隔离 | 训练数据权限与记忆泄漏需治理 |
| 全局性任务 | 需覆盖式检索或聚合 | 需验证位置、干扰和证据利用 | 不能凭权重提供当前全库证据 |
| 注入新事实 | ✅ 强 | ✅（临时） | ❌ 弱 |
| 改风格/格式 | 弱 | 弱（靠 prompt） | ✅ 强 |

## 六、组合策略（实战里通常是「既要又要」）

- **RAG + 长上下文**：用检索缩小范围，把召回到的较长片段塞进长窗口，兼顾精准与全局——主流做法。
- **RAG + 微调**：微调让模型**更会用检索内容**（遵循引用格式、领域口吻），知识仍走 RAG 保持时效。
- **长上下文 + 微调**：微调固定任务范式，长上下文喂具体材料。
- **三者皆可叠**：微调定行为 + RAG 供知识 + 长上下文承载本次材料。

## 七、选型决策路径

按问题性质快速判断：

1. **最新/私有材料是否能在预算内完整提供？** → 少量可直接入上下文；大库或频繁查询可先建检索基线。
2. **要不要可溯源、可按权限隔离？** → RAG 与长上下文都必须显式实现；单靠微调权重不能满足来源证明。
3. **是不是单次任务需要一整篇/整库的全局理解？** → 是 ⇒ **长上下文**（或 RAG 召回大块 + 长窗口）。
4. **是不是要稳定的输出格式/领域风格/特定行为？** → 是 ⇒ **微调**（LoRA 起步）。
5. **知识更新频繁吗？** → 频繁 ⇒ 别用微调装知识，用 **RAG**。
6. **预算与时效**：先用 **RAG / 长上下文 + Prompt** 快速验证；确有稳定行为需求且数据充足，再补**微调**。

> 经验法则：**能用 RAG/Prompt 解决就别先微调**；微调是「最后一公里」的行为对齐，不是知识灌输的首选。

## 高频追问

### 决策交付：不只写一个技术名

假设任务是按有效日期回答公司政策，当前用户只能看部分政策。固定同一授权快照和问题集，分别运行「可见全文入上下文」「检索后入上下文」「检索加长片段」。检索方案单独测证据覆盖；所有方案都测答案正确、引用支持、日期判断和无答案拒答。再用正确证据直供生成器定位证据利用问题。

报告索引/训练前期成本、每次请求成本、更新传播、p95 延迟与失败切片。长上下文缓存命中能改变成本，RAG 多轮检索也可能更贵；不能从表格中的技术类别直接排序价格。Prompt 或微调改善引用格式，不证明引用真实，更不能代替 ACL。

本文沿用的选型口诀是记忆辅助，不是机制定律：微调也能记忆事实，但事实更新、删除、逐用户权限与来源追踪通常更难治理。来源入口：[原始 RAG 论文](https://arxiv.org/abs/2005.11401)、[Lost in the Middle](https://arxiv.org/abs/2307.03172)。本轮未重新读取论文全文，不补造审校日期；决策练习不是模型实测。

1. **RAG、长上下文、微调能不能互相替代？** 不能，解决的问题不同：RAG 管知识与时效，长上下文管单次大材料，微调管风格/格式/能力，实战常组合。
2. **为什么不推荐用微调来注入事实知识？** 易灾难性遗忘、记不牢、不可溯源，且知识一变就要重训；事实知识交给 RAG 更合适。
3. **长上下文会取代 RAG 吗？** 少量可见材料可直接入上下文，大库通常仍需筛选。引用与权限不是 RAG 独有能力；比较实际证据利用、更新与预算后再决定。
4. **什么时候该选微调？** 需要稳定输出格式、领域口吻、特定任务行为，且有足够高质量数据时；优先 LoRA/QLoRA。
5. **「迷失在中间」是什么？** 关键信息位于长上下文中部时模型易忽略，是长上下文方案的已知弱点，可用重排/把要点前置缓解。
6. **预算有限怎么排优先级？** 先 Prompt/长上下文 → 再 RAG → 最后才微调，能不训练就不训练。
7. **RAG + 微调怎么配合？** 知识走 RAG 保时效与溯源，微调让模型更会遵循引用格式与领域风格，各司其职。
